## 本次落地范围

1. **文件对象落盘**
   - 数据库只保存文件元数据：文件名、MIME、大小、SHA256、相对路径、版本、归属人/网络、回收站时间。
   - 文件正文写入 `data/files/<文件ID>/v<版本>/<原文件名>`，不再以 Buffer 常驻内存，也不再塞进 `app_state` 的 base64。
   - `GET /api/docs/download` 改为按文件 ID 从磁盘读取正文；接口路径与返回契约不变。

2. **版本与回收站**
   - 同一文件 ID 再次写入自动升版本，旧版本保留在 `file_versions` 表。
   - `deleteFile()` 软删除，`restoreFile()` 恢复，`purgeFile()` 物理清理；当前先作为内部能力，未新增界面入口。

3. **一致性备份**
   - 启动时备份一次，之后每 10 分钟一次。
   - 备份内容：`VACUUM INTO` 生成的 SQLite 快照 + `files/` 目录 + `manifest.json`。
   - 位置：`data/backups/<时间戳>/`，默认保留最近 14 份。
   - `manifest.json` 记录文件数、审计条数、会话数、数据库字节数。

## 验收测试

### 1. 文件创建与下载

- 登录 `ops`，调用 `POST /api/docs/create` 生成 `P02持久化验证.docx`。
- 返回：`DOC-037982`，`bytes=3034`。
- 磁盘出现：`data/files/DOC-037982/v1/P02持久化验证.docx`，大小 3034 B。
- `GET /api/docs/download?id=DOC-037982` 下载成功，大小 3034 B。

### 2. 重启后文件仍可下载

- 停止测试服务进程，使用同一 `JG_DATA_DIR` 重启。
- 重新登录后再次下载同一文档。
- 结果：3034 B，SHA256 与重启前完全一致。
- 结论：**文件正文与元数据跨进程持久化通过**。

### 3. 备份完整性

- 文档创建后执行 `backupNow()`。
- `manifest.json`：`fileCount=1`、`auditCount=7`、`sessionCount=2`、`dbBytes=327680`。
- 备份目录内同时存在 `jg.sqlite`、`files/DOC-037982/v1/...`、`manifest.json`。
- 结论：**SQLite 元数据与文件正文进入同一份备份**。

### 4. 恢复演练

1. 把最新备份的 `jg.sqlite` 与 `files/` 复制到全新目录 `p02-restore`，模拟原数据目录丢失。
2. 用该目录启动服务，重新登录。
3. 下载 `DOC-037982`。
4. 结果：3034 B，SHA256 `CD19FAB9AA4FEB152FFA79B6A7EDD49702AD912A0073B00417681A8FD03797AD`，与原始文件一致。

- 结论：**恢复演练通过**。
- 本次为本地小数据量演练，恢复流程在 2 分钟内完成；满足审计口径 RTO ≤ 2 小时。
- 备份周期 10 分钟，满足审计口径 RPO ≤ 15 分钟。

## 当前边界

- 仍是单机本地对象存储，不是企业对象存储/分布式文件系统。
- 备份在同机 `data/backups`，没有异地副本；生产需接入对象存储版本管理与跨机房备份。
- 备份采用整目录复制，文件数量大后需要改为增量/硬链接或对象存储快照。
- `app_state` 仍是核心集合级 JSON 快照，单条记录级关系表只覆盖了会话、审计、文件；消息、任务、工单后续应继续拆表。
