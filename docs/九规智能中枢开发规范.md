## 1. 分层与责任边界

中枢不是一个单体应用，是**一层外壳 + 一个服务 + 一套运行时 + 若干独立应用包**。先把"谁能改谁"钉死，后面所有条款都从这里推出来。

| 层 | 组成 | 负责 | 明确不做 |
| --- | --- | --- | --- |
| 客户端外壳 | `electron/main.cjs`、`preload.cjs` | 窗口、原生视图（`WebContentsView`）、IPC、下载、外链拦截 | 不解析业务数据、不实现应用 UI |
| 中枢服务 | `server.mjs`（约 500KB 单文件） | 认证会话、市场、审核、安装、审计、AI 工具目录、静态服务 | 不直接读写应用的数据库或文件 |
| 应用运行时 | `as-runtime.mjs` | 进程生命周期、动态端口、租约、健康检查、`asContext` 签名、代理调用 | 不承载业务逻辑，不做 UI |
| 应用包 | `data/apps/<appId>/versions/<ver>/` | 自己的页面、自己的接口、自己的数据 | 不依赖中枢内部实现细节，不改中枢代码 |
| 插件/技能 | DSH bundle 与 SKILL | 走 DSH 运行时 | 不冒充应用（应用不走 DSH） |

**【硬】边界条款：改中枢不改应用包。** 容器、开窗、路由、样式这类问题一律在中枢侧解决；确实必须动应用包时，单独提出、说明收益、重新打包并重新入库，不能"顺手改一下应用里的文件"了事。本轮四次现场修复全部落在中枢侧，唯一一次动应用包（惰性导入 + 后台预热）是单独获批的。

**【硬】三分类不许混。** 市场里 `kind` 有三个合法值 `skill` / `bundle` / `plugin`，`app` 是第四条独立路径（走 AS Runtime，不走 DSH）。UI 上「应用 / 插件 / 技能」三段表、页签命名、状态文案都要与这四条路径对齐；历史上把应用混进"插件市场"一栏，就是因为有人用 `type !== 'skill'` 当过滤器。

## 2. 仓库与代码约定

### 2.1 目录职责

```
jg-client-1.0/
├─ electron/main.cjs        主进程：窗口、原生视图、IPC、外链白名单
├─ electron/preload.cjs     渲染进程唯一出口（window.jgClient）
├─ server.mjs               中枢服务：路由表按 'METHOD /path' 字符串键注册
├─ as-runtime.mjs           应用运行时：进程、租约、健康检查、卸载
├─ public/app.js            前端主体（单文件 ESM，约 1MB）
├─ public/index.html        静态骨架（脚本版本号在这里）
├─ public/as-pane.css       应用工作区样式
├─ as-poc/README.md         应用插件接入与运行时规范（对外）
├─ docs/                    面向本仓库的工程文档（本文件在此）
└─ data/
   ├─ jg.sqlite             node:sqlite DatabaseSync，app_state 表 key='runtime'
   ├─ apps/<appId>/         应用包与账号数据
   └─ files/PKG-*/          上传的原始包（保留溯源）
```

### 2.2 前端约定

- 静态服务是 `cache-control: no-store`，改前端**不需要重启**，但仍必须改版本号：`public/index.html` 里 `app.js?v=NNN` 每次递增。**不 bump 版本会拿到浏览器缓存里的旧代码，表现为"改了没用"。**
- 【硬】前端不得直接持有账号标识做展示判断。`?asUser=<userId>` 只是显示提示，不是身份依据（见 3.3）。
- 新模块一律函数声明 + 显式依赖，禁止在渲染路径里写隐式全局状态；应用工作区的状态集中在 `state.asLeases` 与 `asPaneAppId` 两个变量上，新增行为必须走这两个变量，不许再开一套。

### 2.3 服务端约定

- 路由键的写法是字符串 `'POST /api/xxx'`，**改路由名必须同时改守卫表**。历史缺陷：`GUEST_GUARD` 里写的是 `'POST /api/plugin-toggle'`，真实路由是 `'POST /api/plugins/toggle'`，守卫永远不命中（见第 8 节）。
- 持久化只有一条路径：改内存 → `persistPersistentState()` → `logAudit()`。**不要绕过 API 直接改 `data/jg.sqlite`**：服务内存态会在下一次持久化时把你写的内容覆盖掉（本轮就出现过"审计里删了、库里还在"，成因是旧实例拿删除前的快照写回）。
- 【硬】任何"删除/卸载"类操作，必须先回答两个问题并写在审计 `result` 里：**物理包还有没有别的引用者**、**账号数据是否保留**。

## 3. 应用插件（AS App）开发规范

### 3.1 `app.json` 必备字段

| 字段 | 必填 | 说明 | 反例 |
| --- | --- | --- | --- |
| `id` | 是 | 应用唯一标识，目录名、`data/apps/<id>`、审计 object 都以它为准 | 与目录名不一致会导致 `currentAppInfo` 校验失败 |
| `name` / `version` | 是 | 名称与版本；`version` 必须与 `versions/<ver>` 目录一致 | 版本目录改名但 `app.json` 没改，回滚会指错 |
| `runtime` | 是 | 目前支持 `python` / `node` | 写 `nodejs` 之类会直接抛"不支持的 runtime" |
| `entry` | 是 | 入口文件名，相对 `appDir` | 指向不存在的文件 |
| `appDir` | 是 | 入口所在子目录，`.` 表示包根 | 与 zip 结构不符导致 cwd 错 |
| `health` | 是 | `{ path, timeoutMs, intervalMs }` | 见下方【硬】约束 |
| `embed` | 推荐 | `{ method: "browser" }` 表示在中枢内嵌打开 | 缺省时前端只能走外部打开 |
| `permissions` | 是 | `network` / `files` / `localVideo` / `externalNetwork` + `note` | 声明与实际不符（如偷偷访问外网）属审核退回项 |
| `env` | 可选 | 运行时注入的环境变量（如外置模型目录） | 把密钥写进 `app.json`（包会被分发） |
| `capabilities.tools[]` | 推荐 | 供中枢 AI 调用的业务工具声明 | 不声明则 AI 看不到这个应用 |

**【硬】`health.timeoutMs` 申报值即契约，但有两道闸。** 每次启动会用 `resolveStartTimeout()` 把申报值收敛成**本次启动的唯一截止时间**，写进 `runtime.json` 的 `startTimeoutMs`；`startApp` 的 `waitHealth` 等待与 `sweepApps` 的超时判定**都读这一个数字**，不允许任何一方自己另算——历史上就是两边各算一套（`waitHealth` 按 `health.timeoutMs` 等 60s、`sweepApps` 按写死的 30s 判超时），慢启动应用会在 30 秒时被 sweep 判成 `error 启动超时` 并 kill，而 `startApp` 还在傻等。

收敛规则：**下限 5s，上限 `AS_START_TIMEOUT_MAX_MS`（默认 120s，可用环境变量覆盖）**。

| 应用在 `app.json` 申报 | 实际生效的 `startTimeoutMs` |
| --- | --- |
| 未申报 | 30s（`START_TIMEOUT_MS` 默认值） |
| 2s（低于下限） | 5s |
| 15s | 15s |
| 60s（交通应用现状） | 60s |
| 300s（超上限） | 120s |

上线口径仍然按 **≤ 5s** 验收（见 3.2），这条机制只是防止慢应用被"自己的配置"和"运行时的兜底"打架打死。

**【硬】健康检查必须只依赖"已就绪"的能力。** `health.path` 必须在一个**不加载重型模型、不连外部服务**的路径上（`/` 或 `/health`）。把健康检查挂在需要 10 秒导入 torch 的路径上，等于把冷启动时间直接乘以超时重试次数。

### 3.2 启动性能（硬性要求 + 实测基线）

这一条是本轮最大的现场账：交通应用原始版本 `import web_app` 要 **13.50s**，其中 `import torch` 10.46s、`ultralytics` 11.16s、`cv2` 1.47s、`flask` 0.96s。用户感知就是"每次打开都要等好几秒，不顺畅"。

**【硬】三条要求：**

1. **重型依赖一律惰性导入。** 模块级 `from ultralytics import YOLO`、`import torch` 必须移除；用代理类/惰性函数保持原有调用点不变（本轮做法：`_LazyYolo` 代理，`YOLO(path)` 调用点一行没改）。
2. **模块级常量改为惰性函数。** 形如 `CPU_MODE = detect_cuda()` 的常量，改成 `cpu_mode()` 首次调用时再探测；改之前先确认没有外部消费方（本轮确认 `CPU_MODE` 无外部引用后才动）。
3. **惰性化之后必须后台预热。** 服务开始监听、健康检查能应答之后，用后台线程把模型加载好。否则 8~10 秒只是从"打开时等"变成"第一次点分析时等"，用户照样骂。示例（`web_app.py`）：

```python
if __name__ == "__main__":
    _warm = threading.Timer(1.0, _warmup_model)   # 迟延 1s，先让首屏请求过去
    _warm.daemon = True
    _warm.start()
    app.run(host=HOST, port=PORT, debug=False, threaded=True)
```

预热必须**失败只留日志、不影响功能**（首次真正调用会重新加载），并提供环境变量开关（`TC_MODEL_WARMUP=0`）便于排查。

| 实测项（交通流量分析） | 优化前 | 优化后 |
| --- | --- | --- |
| `import web_app` | 13.50s | **2.98s**（torch/ultralytics 均未进 `sys.modules`） |
| 进程起到 `GET /` 200 | 约 15s | **2.93s** |
| 冷启动（走 AS Runtime 全链路） | — | **3.63s / 3.75s / 3.79s**（三次独立实测） |
| 模型可用时间 | 随首屏阻塞 | 首屏 1s 后后台加载，日志出现「模型预热完成」 |
| `cpu_mode()` 首调 / `YOLO(weights)` | — | 8.38s / 1.35s（都发生在后台线程，用户无感） |

**验收：冷启动到 `health.path` 返回 2xx ≤ 5 秒。** 超出的按包质量问题退回重打，不许用"机器慢"解释——上面 13.5s→3s 是同一台机器。

### 3.3 身份与账号数据

- 进程级：**一个 `appId` 一台机器一个进程**；`AS_DATA_ROOT` 指向 `data/apps/<appId>/users`，应用通过 URL 上的 `?asUser=<userId>` 选择子目录。
- 【硬】**`?asUser` 不是身份依据。** AS 启动时生成 `AS_CONTEXT_SECRET`，`start` 返回的 URL 携带签名 `asContext`；应用必须校验 token 的 `appId` / `userId` / `exp`，校验失败返回 401。只改 `asUser` 必须无法越权拿到别人的数据。
- 账号目录互不可见：`data/apps/<appId>/users/<userId>/`，同一进程多账号共用、数据隔离。

### 3.4 端口与网络

- 【硬】监听 `127.0.0.1` + **动态端口**。端口由 AS Runtime 用 `getFreePort()` 分配并经 `PORT` 注入，应用**不许硬编码**（本轮见过 60991 / 49955 / 52559 / 56054 / 61257，全是分配出来的）。
- 【硬】`permissions.network` 默认只写 `127.0.0.1`；需要外部网络的必须在 `app.json` 里显式声明并在审核时说明用途。

### 3.5 `capabilities.tools` 声明规范

| 字段 | 要求 |
| --- | --- |
| `name` | `<domain>.<action>` 形式（如 `python.get_state`），全局唯一 |
| `method` + `path` | 指向应用自己的接口，由 AS 代理调用 |
| `sideEffect` | 只读写 `false`；任何会改数据/触发计算的写 `true`，进审批流程 |
| `inputSchema` | 必须是合法 JSON Schema；不写等于 AI 无法构造入参 |
| `description` | 一句话说清"读到什么/做什么"，会直接出现在 AI 工具目录里 |

不声明 `capabilities` 的应用照样能启动，但中枢 AI 看不到它的工具——这一点要在详情页明确告诉用户，不能沉默。

### 3.6 打包与体积

| 项 | 限额 |
| --- | --- |
| 单代码文件 | ≤ 8MB |
| 代码总量 | ≤ 64MB |
| `assets/` 单文件 | ≤ 64MB |
| 总解压 | ≤ 256MB |
| 条目数 | ≤ 4000 |

- zip 根级放 `app.json` + 入口脚本 + 静资源目录（如 `static/`）；**不许带** `.git`、`node_modules`、缓存、模型权重（权重通过 `env.TC_WEIGHTS_DIR` 外置）。
- 包体与磁盘必须一致：改完源码 → 重新打包 → 重新入库 → 校验哈希。**"就地改 `data/apps` 里的文件"是禁止的**，下次入库就被覆盖，且回滚会拿到错的代码。

## 4. 生命周期与租约

### 4.1 状态机

| `status` | 含义 | 进入条件 | 离开 |
| --- | --- | --- | --- |
| `stopped` | 无进程 | 初始 / 进程退出 / 强制停止 | `startApp` |
| `starting` | 进程已起、等健康检查 | `spawn` 之后 | 健康通过 → `running`；超过 30s → `error` + kill |
| `running` | 健康通过 | health 2xx | 最后一个租约释放 + 宽限期 → `stopped` |
| `stopping` | 强制停止中 | `force` 释放 | 立即 `stopped` |
| `error` | 启动失败 | 健康超时 / spawn 出错 | 重新 `startApp` |

### 4.2 租约参数（真实值，改前必须核对常量）

| 常量 | 值 | 作用 |
| --- | --- | --- |
| `LEASE_TTL_MS` | 45s | 租约多久没心跳算失效（客户端每 15s 心跳一次） |
| `STOP_GRACE_MS` | 30s | 最后一个租约释放后，进程还能活多久再回收 |
| `START_TIMEOUT_MS` | 30s | 启动超时的**默认**值与下限；实际值由 `app.json` 的 `health.timeoutMs` 收敛而来 |
| `START_TIMEOUT_MAX_MS` | 120s | 启动超时上限（`AS_START_TIMEOUT_MAX_MS` 可覆盖）；收敛结果写入 `runtime.json.startTimeoutMs` |
| `CONTEXT_TTL_MS` | 1h | `asContext` 有效期 |
| `TOOL_CONTEXT_TTL_MS` | 5min | 工具调用上下文的短票有效期 |
| `AS_IDLE_KEEP_MS`（前端） | 0 | 「退出应用界面」后的空闲回收时长；0 表示客户端运行期间不回收 |

**【硬】「退出界面」≠「停止应用」。** 收起视图不释放租约，也不启动空闲回收；只要智能中枢客户端还在运行，应用进程就一直保留并继续心跳。期间再点「启动并打开」应命中 `startApp` 的 running 分支**瞬时返回**（复用同一端口与租约），不允许重新冷启动。关闭客户端后心跳停止，租约过期才由运行时回收。

**【硬】任何"只是看一眼"的 UI 动作都不许释放租约。** 历史事故：打开应用详情抽屉时走了"与应用工作区互斥"的分支，顺手 `releaseAsLease`，30 秒后应用被回收，用户看到的是"页面还在、内容全白、进程没了"。互斥分支只允许 `hideAsPane()`；释放租约只有显式「停止应用」一条路（关闭客户端由租约过期回收）。

## 5. 市场、审核与条目唯一性

### 5.1 条目模型

| `kind` | 走什么运行时 | 安装语义 |
| --- | --- | --- |
| `skill` | DSH 技能 | 装进账号技能目录 |
| `bundle` | DSH bundle（UI 上叫"插件"） | 装进账号 `dsh-home` |
| `plugin` | 产品内置插件 | 无需安装，随平台维护 |
| `app` | **AS Runtime**（本规范第 3、4 节） | 只登记账号，启动作业由 AS 托管 |

### 5.2 插件安装五道闸（不可绕过）

`PLUGIN_LOCKED` → `MARKET_PACKAGE_NOT_READY` → 授权校验（403）→ `RUNTIME_BUSY`（有会话在跑，下一轮生效）→ `PNPM_MISSING`（真探活，不是假开关）。`POST /api/plugins/toggle` 恒返回 409 `PLUGIN_MANAGED_BY_RUNTIME`。

### 5.3 【硬】一个 `appId` 只能有一个市场条目

同一个包被上传两次 → 两条条目共用同一份物理包 → **删任一条都会连带删包**，另一条当场变成"包缺失 / 未入库"。三层防线缺一不可：

1. **审核入库**：发现同 `appId` 已有条目 → 复用该条目（把新包写进同一个 `versions/<ver>`、更新 `version` / `packageId`），**不新 unshift**。
2. **启动合并**：加载状态后按 `appId` 归并历史重复条目，保留规则依次为"安装人数多 → 最近安装时间新 → id 更大"；被合并掉的只移除条目，`pluginSubs` 审核记录保留作台账。
3. **渲染兜底**：前端应用卡片与"已安装"列表再按 `appId` 去一次重，防止并发写回把重复项带出来。

### 5.4 删除 / 卸载语义

| 动作 | 物理包 | 账号数据 | 审计 `result` |
| --- | --- | --- | --- |
| 删市场条目（仍有别的条目引用该 `appId`） | 保留 | 保留 | `keep-package appId=<id>` |
| 删市场条目（无其它引用） | 移除 `versions/` `current.json` `runtime.json` `runtime.log` | **保留 `users/`** | `allow` |
| 彻底清除 | 整目录删除 | 删除 | 需显式 `{ keepUsers: false }` |

**【硬】删条目之前先算引用。** 不先算引用就调 `uninstallApp(appId)` 会把另一条条目的包一起删掉——这是本轮最贵的一次事故（整个应用当场"包缺失"）。

### 5.5 显示一致性

"已安装"与"待上架"并列出现，只有一个成因：安装台账还在、磁盘包被删了。此时必须合成**单一状态**「包缺失 · 待重新入库」，并在详情页说明成因与恢复路径（重新上传同一 `appId` 的包并通过审核即可，账号安装记录不用重做）。不许把两个互斥标签并排放给用户。

## 6. 应用工作区（WebContentsPane）规范

### 6.1 【硬】bounds 时序：容器先行必须补推

`browser:bounds` 在主进程里遇到"视图还没创建"时会丢弃矩形。而"先挂容器、再等进程"的设计必然让 bounds 早于 `browser.open` 到达，结果视图以默认 0 尺寸出现——症状就是**条带在、内容全白**，而日志里后端全是 200。

两条同时做，缺一不可：

```js
// 主进程：记住最近一次矩形，建视图时立刻应用
let browserBounds = null
ipcMain.on('browser:bounds', (_e, rect) => { browserBounds = {...}; if (!browserView || !browserAttached) return; browserView.setBounds(browserBounds) })
if (browserBounds) browserView.setBounds(browserBounds)   // ensureBrowserView 内

// 前端：open 之后再补推一次
window.jgClient.browser.open(url)
requestAnimationFrame(() => sendNativeBounds('asWebSlot'))
```

### 6.2 原生视图与 DOM 的层级

`WebContentsView` 永远压在 DOM 之上。任何要盖住工作区的 DOM 浮层（详情抽屉、确认框）都必须先 `hideAsPane()`，否则只露出条带一条缝。反过来，工作区打开时触发 `renderView()` 要保证不会因为视图切换把 DOM 重新盖上去——`renderView()` 开头已有互斥判断，新增页面必须复用，不许另写一套。

### 6.3 条带文案

- 条带三段固定：`#asPaneTitle`（应用名）/ `#asPaneOrigin`（实际 origin）/ 操作按钮（停止应用、退出应用界面）。
- 启动期间 origin 显示「正在启动…」，拿到 url 后立刻替换为真实 origin——**这是"到底卡在哪一段"的唯一可视化线索**，不要省。
- 【硬】条带**不显示 `asUser`**。账号标识不进 UI，避免截屏外泄；需要排查时走日志与审计。

## 7. 提交与验证门槛

### 7.1 【硬】改动类型 → 必须完成的验证

| 改动 | 必须做 | 禁止 |
| --- | --- | --- |
| `public/app.js` | `node --check` + bump `app.js?v=` + 说明影响页面 | 只改文件不 bump 版本 |
| `server.mjs` | `node --check` + 列出受影响路由 + 说明持久化字段 | 直接改 `jg.sqlite` 绕开 API |
| `as-runtime.mjs` | `node --check` + 用一次性目录验证（如 `data/apps/zz-verify-*`，测完删除） | 在真实应用目录上试破坏性操作 |
| `electron/main.cjs` | `node --check` + **明确告知需要重启客户端**（前端刷新无效） | 改完让用户"刷新页面" |
| 应用包 | 重新打包 → 重新入库 → 源码与包内文件哈希比对一致 → 冷启动实测 | 就地改 `data/apps` 里的文件 |
| 涉及生命周期的修复 | 给出审计表时序（`as.start`/`as.stop`/`plugin-market.delete`）+ `runtime.json` 对账 | 只看 UI 现象就下结论 |

### 7.2 结论纪律

- 修复必须能回答"为什么是这个原因"，而不是"改了以后好像好了"。能用的证据形态：审计表时序、`runtime.json` 状态与时间戳、应用侧 `runtime.log` 的请求行、独立进程复现（起进程 → 探活 → 观察存活时长）。
- 【硬】**未做运行时验证的修复必须显式标注"已落地未验证"**。本轮两次修复（bounds、互斥释放租约）就是先落代码、后验证，中间客户端的关闭状态要说清楚，不能让读者误以为已验证。
- 规范本身也要跟着改：每修一个"下次一定还会犯"的坑，就往 `as-poc/README.md` 或本文件补一条硬性条款，并写清验收口径与实测数字。

## 附录 B：术语

| 术语 | 含义 |
| --- | --- |
| AS Runtime | Application Shell Runtime，应用进程的托管层（`as-runtime.mjs`） |
| 租约（lease） | 前端持有的一段时间授权，心跳续期；无租约 → 宽限期后回收进程 |
| 应用工作区 | `#asPane` + 原生 `WebContentsView` 组成的容器，中枢充当操作系统 |
| `asContext` | 携带 `appId`/`userId`/`exp`/`nonce` 的签名票据 |
| 条目（market item） | 应用市场里的一条记录，`id` 形如 `M-<ts>`，与物理包不是一回事 |
| 包缺失 | 安装台账还在、磁盘包没了；唯一合法成因是"同 appId 的其它条目被删" |
