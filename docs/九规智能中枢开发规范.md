## 1. 分层与责任边界

中枢不是一个单体应用，是**一层外壳 + 一个服务 + 一套运行时 + 若干独立应用包**。先把"谁能改谁"钉死，后面所有条款都从这里推出来。

| 层 | 组成 | 负责 | 明确不做 |
| --- | --- | --- | --- |
| 客户端外壳 | `electron/main.cjs`、`preload.cjs` | 窗口、原生视图（`WebContentsView`）、IPC、下载、外链拦截 | 不解析业务数据、不实现应用 UI |
| 中枢服务 | `server.mjs`（约 500KB 单文件） | 认证会话、市场、审核、安装、审计、AI 工具目录、静态服务 | 不直接读写应用的数据库或文件 |
| 应用运行时 | `as-runtime.mjs` | 进程生命周期、动态端口、租约、健康检查、`asContext` 签名、代理调用 | 不承载业务逻辑，不做 UI |
| 应用包 | `data/apps/<appId>/versions/<ver>/` | 自己的页面、自己的接口、自己的数据 | 不依赖中枢内部实现细节，不改中枢代码 |
| 插件/技能 | DSH bundle 与 SKILL | 走 DSH 运行时 | 不冒充应用（应用不走 DSH） |

**【硬】边界条款：改中枢不改应用包。** 容器、开窗、路由、样式这类问题一律在中枢侧解决；确实必须动应用包时，单独提出、说明收益、重新打包并重新入库，不能"顺手改一下应用里的文件"了事。本轮四次现场修复全部落在中枢侧，唯一一次动应用包（惰性导入 + 后台预热）是单独获批的。

**【硬】三分类不许混。** 市场里 `kind` 有三个合法值 `skill` / `bundle` / `plugin`，`app` 是第四条独立路径（走 AS Runtime，不走 DSH）。UI 上「应用 / 插件 / 技能」三段表、页签命名、状态文案都要与这四条路径对齐；历史上把应用混进"插件市场"一栏，就是因为有人用 `type !== 'skill'` 当过滤器。

## 2. 仓库与代码约定

### 2.1 目录职责

```
jg-client-1.0/
├─ electron/main.cjs        主进程：窗口、原生视图、IPC、外链白名单
├─ electron/preload.cjs     渲染进程唯一出口（window.jgClient）
├─ server.mjs               中枢服务：路由表按 'METHOD /path' 字符串键注册
├─ as-runtime.mjs           应用运行时：进程、租约、健康检查、卸载
├─ public/app.js            前端主体（单文件 ESM，约 1MB）
├─ public/index.html        静态骨架（脚本版本号在这里）
├─ public/as-pane.css       应用工作区样式
├─ as-poc/README.md         应用插件接入与运行时规范（对外）
├─ docs/                    面向本仓库的工程文档（本文件在此）
└─ data/
   ├─ jg.sqlite             node:sqlite DatabaseSync，app_state 表 key='runtime'
   ├─ apps/<appId>/         应用包与账号数据
   └─ files/PKG-*/          上传的原始包（保留溯源）
```

### 2.2 前端约定

- 静态服务是 `cache-control: no-store`，改前端**不需要重启**，但仍必须改版本号：`public/index.html` 里 `app.js?v=NNN` 每次递增。**不 bump 版本会拿到浏览器缓存里的旧代码，表现为"改了没用"。**
- 【硬】前端不得直接持有账号标识做展示判断。`?asUser=<userId>` 只是显示提示，不是身份依据（见 3.3）。
- 新模块一律函数声明 + 显式依赖，禁止在渲染路径里写隐式全局状态；应用工作区的状态集中在 `state.asLeases` 与 `asPaneAppId` 两个变量上，新增行为必须走这两个变量，不许再开一套。

### 2.3 服务端约定

- 路由键的写法是字符串 `'POST /api/xxx'`，**改路由名必须同时改守卫表**。历史缺陷：`GUEST_GUARD` 里写的是 `'POST /api/plugin-toggle'`，真实路由是 `'POST /api/plugins/toggle'`，守卫永远不命中（见第 8 节）。
- 持久化只有一条路径：改内存 → `persistPersistentState()` → `logAudit()`。**不要绕过 API 直接改 `data/jg.sqlite`**：服务内存态会在下一次持久化时把你写的内容覆盖掉（本轮就出现过"审计里删了、库里还在"，成因是旧实例拿删除前的快照写回）。
- 【硬】重启收口：`recoverInterruptedTasks()` 把上一轮遗留的 `chat-run` / `automation-run`（running、queued）标为 `interrupted`，保留会话、指令、DSH session 与 `userId`，**不自动重放已发出的工具动作或付费请求**；chat-run 由前端回到原会话发恢复指令续跑，automation-run 等下次调度重新执行。任务按 `userId` 隔离，恢复/重试接口只能操作本人任务。
- 【硬】任何"删除/卸载"类操作，必须先回答两个问题并写在审计 `result` 里：**物理包还有没有别的引用者**、**账号数据是否保留**。

## 3. 应用插件（AS App）开发规范

### 3.1 `app.json` 必备字段

| 字段 | 必填 | 说明 | 反例 |
| --- | --- | --- | --- |
| `id` | 是 | 应用唯一标识，目录名、`data/apps/<id>`、审计 object 都以它为准 | 与目录名不一致会导致 `currentAppInfo` 校验失败 |
| `name` / `version` | 是 | 名称与版本；`version` 必须与 `versions/<ver>` 目录一致 | 版本目录改名但 `app.json` 没改，回滚会指错 |
| `runtime` | 是 | 目前支持 `python` / `node` | 写 `nodejs` 之类会直接抛"不支持的 runtime" |
| `entry` | 是 | 入口文件名，相对 `appDir` | 指向不存在的文件 |
| `appDir` | 是 | 入口所在子目录，`.` 表示包根 | 与 zip 结构不符导致 cwd 错 |
| `health` | 是 | `{ path, timeoutMs, intervalMs }` | 见下方【硬】约束 |
| `embed` | 推荐 | `{ method: "browser" }` 表示在中枢内嵌打开 | 缺省时前端只能走外部打开 |
| `permissions` | 是 | `network` / `files` / `localVideo` / `externalNetwork` + `note` | 声明与实际不符（如偷偷访问外网）属审核退回项 |
| `env` | 可选 | 运行时注入的环境变量（如外置模型目录） | 把密钥写进 `app.json`（包会被分发） |
| `capabilities.tools[]` | 是（要 AI 调用时） | 供中枢 AI 调用的业务工具声明；不声明则 AI 只能发现应用和读数据，不能调用业务接口 | 声明了 `name` 却没有对应路由；或把写操作写成 `sideEffect:false` |
| `capabilities.resources[]` | 是（要 AI 读业务数据时） | 只读资源声明，如历史列表、状态、最近一次结果；与 tools 一样进入 AI 目录 | 把资源当工具、把需要审批的写操作塞进 resources |

**【硬】新应用要进入中枢 AI 可调用目录，`capabilities` 是合同，不是可选项。**

平台侧已经改成动态发现：应用安装后，`app_list` / `capability_list` 会实时读取 `data/apps/<id>/current.json` 和对应版本的 `app.json`，不需要每次改 `server.mjs`。但这只解决“找得到”；“调得通”仍取决于应用是否把工具、资源、路由和参数声明全。未声明 `capabilities` 的应用可以启动、可以被 AI 看到、可以被读数据目录，但不能被调用业务接口——详情页必须明确写出这一点，不能把“应用已安装”说成“AI 已接入”。

**【硬】`health.timeoutMs` 申报值即契约，但有两道闸。** 每次启动会用 `resolveStartTimeout()` 把申报值收敛成**本次启动的唯一截止时间**，写进 `runtime.json` 的 `startTimeoutMs`；`startApp` 的 `waitHealth` 等待与 `sweepApps` 的超时判定**都读这一个数字**，不允许任何一方自己另算——历史上就是两边各算一套（`waitHealth` 按 `health.timeoutMs` 等 60s、`sweepApps` 按写死的 30s 判超时），慢启动应用会在 30 秒时被 sweep 判成 `error 启动超时` 并 kill，而 `startApp` 还在傻等。

收敛规则：**下限 5s，上限 `AS_START_TIMEOUT_MAX_MS`（默认 120s，可用环境变量覆盖）**。

| 应用在 `app.json` 申报 | 实际生效的 `startTimeoutMs` |
| --- | --- |
| 未申报 | 30s（`START_TIMEOUT_MS` 默认值） |
| 2s（低于下限） | 5s |
| 15s | 15s |
| 60s（交通应用现状） | 60s |
| 300s（超上限） | 120s |

上线口径仍然按 **≤ 5s** 验收（见 3.2），这条机制只是防止慢应用被"自己的配置"和"运行时的兜底"打架打死。

**【硬】健康检查必须只依赖"已就绪"的能力。** `health.path` 必须在一个**不加载重型模型、不连外部服务**的路径上（`/` 或 `/health`）。把健康检查挂在需要 10 秒导入 torch 的路径上，等于把冷启动时间直接乘以超时重试次数。

### 3.2 启动性能（硬性要求 + 实测基线）

这一条是本轮最大的现场账：交通应用原始版本 `import web_app` 要 **13.50s**，其中 `import torch` 10.46s、`ultralytics` 11.16s、`cv2` 1.47s、`flask` 0.96s。用户感知就是"每次打开都要等好几秒，不顺畅"。

**【硬】三条要求：**

1. **重型依赖一律惰性导入。** 模块级 `from ultralytics import YOLO`、`import torch` 必须移除；用代理类/惰性函数保持原有调用点不变（本轮做法：`_LazyYolo` 代理，`YOLO(path)` 调用点一行没改）。
2. **模块级常量改为惰性函数。** 形如 `CPU_MODE = detect_cuda()` 的常量，改成 `cpu_mode()` 首次调用时再探测；改之前先确认没有外部消费方（本轮确认 `CPU_MODE` 无外部引用后才动）。
3. **惰性化之后必须后台预热。** 服务开始监听、健康检查能应答之后，用后台线程把模型加载好。否则 8~10 秒只是从"打开时等"变成"第一次点分析时等"，用户照样骂。示例（`web_app.py`）：

```python
if __name__ == "__main__":
    _warm = threading.Timer(1.0, _warmup_model)   # 迟延 1s，先让首屏请求过去
    _warm.daemon = True
    _warm.start()
    app.run(host=HOST, port=PORT, debug=False, threaded=True)
```

预热必须**失败只留日志、不影响功能**（首次真正调用会重新加载），并提供环境变量开关（`TC_MODEL_WARMUP=0`）便于排查。

| 实测项（交通流量分析） | 优化前 | 优化后 |
| --- | --- | --- |
| `import web_app` | 13.50s | **2.98s**（torch/ultralytics 均未进 `sys.modules`） |
| 进程起到 `GET /` 200 | 约 15s | **2.93s** |
| 冷启动（走 AS Runtime 全链路） | — | **3.63s / 3.75s / 3.79s**（三次独立实测） |
| 模型可用时间 | 随首屏阻塞 | 首屏 1s 后后台加载，日志出现「模型预热完成」 |
| `cpu_mode()` 首调 / `YOLO(weights)` | — | 8.38s / 1.35s（都发生在后台线程，用户无感） |

**验收：冷启动到 `health.path` 返回 2xx ≤ 5 秒。** 超出的按包质量问题退回重打，不许用"机器慢"解释——上面 13.5s→3s 是同一台机器。

### 3.3 身份与账号数据

- 进程级：**一个 `appId` 一台机器一个进程**；`AS_DATA_ROOT` 指向 `data/apps/<appId>/users`，应用通过 URL 上的 `?asUser=<userId>` 选择子目录。
- 【硬】**`?asUser` 不是身份依据。** AS 启动时生成 `AS_CONTEXT_SECRET`，`start` 返回的 URL 携带签名 `asContext`；应用必须校验 token 的 `appId` / `userId` / `exp`，校验失败返回 401。只改 `asUser` 必须无法越权拿到别人的数据。
- 账号目录互不可见：`data/apps/<appId>/users/<userId>/`，同一进程多账号共用、数据隔离。
- 【硬】**生成数据必须落到 `AS_DATA_DIR`，不能落在包目录或版本目录。** `AS_DATA_DIR` 是 AS 注入的“当前账号应用数据根”，已经包含 `users/<userId>`；应用所有上传、产物、历史、转码、数据库都必须以它为根。用 `BASE_DIR` / `versions/<ver>` 当默认值，会在切换账号时把 A 的数据写进 B 的目录，也会让中枢的“全量应用数据”通道看不到。
- 只读发现通道按账号根目录工作：`outputs/`、`data/`、`material/` 等顶层目录都可以，**不要为了“能被 AI 读”再另造一套目录**。文本类（CSV/JSON/TXT/MD/LOG 等）走 `app_data_read`，SQLite 走 `app_data_query`；二进制产物必须由应用自己声明一个工具返回，不要指望平台直接读二进制。
- 应用数据目录里**不要放密钥**。平台会排除 `secret` / `credential` / `token` / `password` / `*.key` / `*.pem` 以及 `*-wal` / `*-shm`，但“平台帮你挡”不是把密钥放进数据目录的理由。

Python 参考写法：

```python
DATA_HOME = os.path.abspath(os.environ.get("AS_DATA_DIR") or BASE_DIR)
OUTPUT_DIR = os.path.join(DATA_HOME, "outputs")
DATA_DIR = os.path.join(DATA_HOME, "data")
HISTORY_FILE = os.path.join(DATA_DIR, "history.json")
```

Node 参考写法：

```js
const dataHome = path.resolve(process.env.AS_DATA_DIR || path.join(home, 'local-data'))
const outputDir = path.join(dataHome, 'outputs')
```

### 3.4 端口与网络

- 【硬】监听 `127.0.0.1` + **动态端口**。端口由 AS Runtime 用 `getFreePort()` 分配并经 `PORT` 注入，应用**不许硬编码**（本轮见过 60991 / 49955 / 52559 / 56054 / 61257，全是分配出来的）。
- 【硬】`permissions.network` 默认只写 `127.0.0.1`；需要外部网络的必须在 `app.json` 里显式声明并在审核时说明用途。

### 3.5 `capabilities.tools` / `capabilities.resources` 声明规范

`tools` 和 `resources` 使用同一套字段；区别是语义：`tools` 是“可执行的业务动作”，`resources` 是“可读取的只读结果/列表/状态”。两者都会进入中枢 AI 的 `app_list` / `capability_list`，都可以由 `app_call` 按 `name` 调用。

| 字段 | 要求 |
| --- | --- |
| `name` | `<domain>.<action>` 形式（如 `python.get_state`、`traffic.latest_output`），应用内唯一；不要起 `get_data` 这种换应用就撞的泛名 |
| `method` + `path` | 指向应用自己的真实路由；`GET` 用于读取，`POST` 用于动作；路径必须能被 AS 代理访问 |
| `sideEffect` | 【硬】只读写 `false`；任何会改数据、触发计算、启动外部进程、提交任务的写 `true`，进审批流程。不要把 `sideEffect` 省略成默认值 |
| `inputSchema` | 【硬】必须是合法 JSON Schema；不写等于 AI 无法构造入参。无参数也要写空对象 `{ "type": "object", "properties": {} }` |
| `outputSchema` | 推荐；写清返回对象的顶层字段，便于模型判断结果结构 |
| `timeoutMs` | 推荐；按接口真实耗时申报。同步接口不要申报成 5s 却实际跑 60s |
| `description` | 一句话说清“读到什么/做什么”，会直接出现在 AI 工具目录里 |

【硬】声明必须与实际一致，以下都属审核退回项：

- `app.json` 声明了 `traffic.latest_output`，但应用没有 `/api/latest_output`；
- 路由存在，但 `name` 与声明不一致；
- 写操作标成 `sideEffect:false`，AI 以为只读，实际改了库；
- `inputSchema` 的必填字段没有默认值，AI 不传就 400；
- 资源接口返回二进制或超大文件，却没有分页/截断。

不声明 `capabilities` 的应用照样能启动，也能被 `app_data_*` 读数据目录；但中枢 AI 看不到它的业务工具，详情页必须明确告诉用户“该应用尚未声明 AI 能力”，不能沉默，也不能用“应用已安装”冒充“已接入”。

平台侧约定：新应用不需要改 `server.mjs`。安装后动态进入目录；第一次 `app_call` 由 AS 懒启动、校验账号上下文、加租约。新增应用只要满足本节和 3.3，就算完成 AI 接入。

### 3.6 打包与体积

| 项 | 限额 |
| --- | --- |
| 单代码文件 | ≤ 8MB |
| 代码总量 | ≤ 64MB |
| `assets/` 单文件 | ≤ 64MB |
| 总解压 | ≤ 256MB |
| 条目数 | ≤ 4000 |

- zip 根级放 `app.json` + 入口脚本 + 静资源目录（如 `static/`）；**不许带** `.git`、`node_modules`、缓存、模型权重（权重通过 `env.TC_WEIGHTS_DIR` 外置）。
- 包体与磁盘必须一致：改完源码 → 重新打包 → 重新入库 → 校验哈希。**"就地改 `data/apps` 里的文件"是禁止的**，下次入库就被覆盖，且回滚会拿到错的代码。

### 3.7 中枢 AI 接入验收（新增强制）

新应用或版本更新进入市场后，必须按下面四项做真实调用验收。只做 `app.json` 静态检查、不跑接口，不算接入完成；只跑一个 `app_call`、不验数据目录，也不算“全量应用数据可读”。

| # | 验收项 | 通过标准 | 证据 |
| --- | --- | --- | --- |
| 1 | 能力发现 | `app_list` 和 `capability_list` 都出现该 `appId`，`declared:true`，`tools/resources` 与 `app.json` 一致 | 保存真实响应，不贴手写目录 |
| 2 | 业务调用 | 对每个 `sideEffect:false` 的 tool/resource 调一次 `app_call`，HTTP 200；写操作只验证到“返回 202 审批单”，不绕过审批 | 记录 `httpStatus`、关键返回字段、运行 ID |
| 3 | 数据可读 | `app_data_list` 能看到该应用当前账号生成的文件；文本能 `app_data_read` 回读；SQLite 能 `app_data_query` 返回表或数据 | 记录文件相对路径、字节数、查询行数 |
| 4 | 边界 | 换账号路径、`../` 越界、密钥/临时文件、写 SQL 都被拒绝；未声明能力的应用只能被发现和读数据，不能调用业务接口 | 记录错误码：`AS_APP_DATA_PATH` / `AS_APP_DATA_SCOPE` / `AS_APP_DATA_SQL` |

【硬】验收结论必须区分：

- **已接入**：1、2、3 都通过，且 4 的拒绝路径有证据；
- **仅发现**：应用在目录里，但无 `capabilities` 或接口未通；
- **仅数据可读**：`app_data_*` 通过，但业务接口未声明或未通；
- **未接入**：目录里没有该应用，或调用返回非 2xx。

禁止用“按钮在”“目录里有”替代表中的 2、3；也禁止用应用自己页面上的成功提示替代中枢 `app_call` 的真实响应。

### 3.8 插件与技能的 AI 接入边界

不要把“应用、插件、技能”混成一句“都能调用”。

| 类别 | 怎样被中枢 AI 看到/调用 | 不能做什么 |
| --- | --- | --- |
| 技能 | 安装到 `data/agents/<userId>/dsh-home/skills/<name>/SKILL.md`；`capability_list` 读取 frontmatter 的 `name` / `description`，模型用 `skill` 工具加载 | 只有目录没有 `SKILL.md`；把技能写成应用工具；声称“已加载”但没实际读文件 |
| 产品插件 | 在 `PRODUCT_MARKET_PLUGINS` 登记，并显式映射成一个模型可见工具（如代码审查的 `mcp__jg__code_review`）；`capability_list` 标 `callable:true` 和 `tool` | 只登记插件、不给工具映射，却写成“AI 可调用” |
| 运行时插件 | `plugins/` 下的 Harness 运行时扩展，由运行时加载；`capability_list` 标 `callable:false` | 把 `jg-spill-age`、`jg-tool-router` 这类运行时插件伪装成对话工具；它们不是给模型点的按钮 |

技能只解决“怎么做事”的提示与流程，不是可执行业务接口；应用工具才走 `app_call`。产品插件若声明了 `callable:true`，必须同时给出真实工具名和调用前置条件（如代码审查需要已绑定项目），并在验收时至少跑通一次；跑不通就降级为“仅登记”。

## 4. 生命周期与租约

### 4.1 状态机

| `status` | 含义 | 进入条件 | 离开 |
| --- | --- | --- | --- |
| `stopped` | 无进程 | 初始 / 进程退出 / 强制停止 | `startApp` |
| `starting` | 进程已起、等健康检查 | `spawn` 之后 | 健康通过 → `running`；超过 30s → `error` + kill |
| `running` | 健康通过 | health 2xx | 显式停止 / 账号切换 / 版本切换 / 卸载 / 进程崩溃 / 中枢退出 → `stopped`；常驻模式下不因无租约回收 |
| `stopping` | 强制停止中 | `force` 释放 | 立即 `stopped` |
| `error` | 启动失败 | 健康超时 / spawn 出错 | 重新 `startApp` |

### 4.2 租约参数（真实值，改前必须核对常量）

| 常量 | 值 | 作用 |
| --- | --- | --- |
| `LEASE_TTL_MS` | 45s | 租约多久没心跳算失效（客户端每 15s 心跳一次）；仅占用计数用途，常驻模式下不据此回收进程 |
| `STOP_GRACE_MS` | 30s | 无租约后的宽限期；仅非常驻模式（`AS_NO_PERSIST=1`）生效 |
| `PERSISTENT`（内置） | 开 | 中枢运行期间应用进程常驻后台；设 `AS_NO_PERSIST=1` 回退到旧的"无租约宽限回收"模式 |
| `START_TIMEOUT_MS` | 30s | 启动超时的**默认**值与下限；实际值由 `app.json` 的 `health.timeoutMs` 收敛而来 |
| `START_TIMEOUT_MAX_MS` | 120s | 启动超时上限（`AS_START_TIMEOUT_MAX_MS` 可覆盖）；收敛结果写入 `runtime.json.startTimeoutMs` |
| `CONTEXT_TTL_MS` | 1h | `asContext` 有效期 |
| `TOOL_CONTEXT_TTL_MS` | 5min | 工具调用上下文的短票有效期 |
| `AS_IDLE_KEEP_MS`（前端） | 0 | 「退出应用界面」后的空闲回收时长；0 表示客户端运行期间不回收 |

**【硬】「退出界面」≠「停止应用」。** 收起视图不释放进程，也不启动空闲回收；只要智能中枢进程还在运行，应用进程就一直保留在后台。期间再点「启动并打开」应命中 `startApp` 的 running 分支**瞬时返回**（复用同一端口与进程），不允许重新冷启动。心跳/租约只用于占用计数与视图状态同步，丢失或断连不触发回收；只有显式停止、账号切换、版本切换、卸载、进程崩溃或中枢退出时才回收。

**【硬】任何"只是看一眼"的 UI 动作都不许停进程。** 历史事故：打开应用详情抽屉时走了"与应用工作区互斥"的分支，顺手 `releaseAsLease`，30 秒后应用被回收，用户看到的是"页面还在、内容全白、进程没了"。互斥分支只允许 `hideAsPane()`；停进程只有显式「停止应用」一条路（卸载、账号切换、版本切换、中枢退出除外）。

## 5. 市场、审核与条目唯一性

### 5.1 条目模型

| `kind` | 走什么运行时 | 安装语义 |
| --- | --- | --- |
| `skill` | DSH 技能 | 装进账号技能目录 |
| `bundle` | DSH bundle（UI 上叫"插件"） | 装进账号 `dsh-home` |
| `plugin` | 产品内置插件 | 无需安装，随平台维护 |
| `app` | **AS Runtime**（本规范第 3、4 节） | 只登记账号，启动作业由 AS 托管 |

### 5.2 插件安装五道闸（不可绕过）

`PLUGIN_LOCKED` → `MARKET_PACKAGE_NOT_READY` → 授权校验（403）→ `RUNTIME_BUSY`（有会话在跑，下一轮生效）→ `PNPM_MISSING`（真探活，不是假开关）。`POST /api/plugins/toggle` 恒返回 409 `PLUGIN_MANAGED_BY_RUNTIME`。

### 5.3 【硬】一个 `appId` 只能有一个市场条目

同一个包被上传两次 → 两条条目共用同一份物理包 → **删任一条都会连带删包**，另一条当场变成"包缺失 / 未入库"。三层防线缺一不可：

1. **审核入库**：发现同 `appId` 已有条目 → 复用该条目（把新包写进同一个 `versions/<ver>`、更新 `version` / `packageId`），**不新 unshift**。
2. **启动合并**：加载状态后按 `appId` 归并历史重复条目，保留规则依次为"安装人数多 → 最近安装时间新 → id 更大"；被合并掉的只移除条目，`pluginSubs` 审核记录保留作台账。
3. **渲染兜底**：前端应用卡片与"已安装"列表再按 `appId` 去一次重，防止并发写回把重复项带出来。

### 5.4 删除 / 卸载语义

| 动作 | 物理包 | 账号数据 | 审计 `result` |
| --- | --- | --- | --- |
| 删市场条目（仍有别的条目引用该 `appId`） | 保留 | 保留 | `keep-package appId=<id>` |
| 删市场条目（无其它引用） | 移除 `versions/` `current.json` `runtime.json` `runtime.log` | **保留 `users/`** | `allow` |
| 彻底清除 | 整目录删除 | 删除 | 需显式 `{ keepUsers: false }` |

**【硬】删条目之前先算引用。** 不先算引用就调 `uninstallApp(appId)` 会把另一条条目的包一起删掉——这是本轮最贵的一次事故（整个应用当场"包缺失"）。

### 5.5 显示一致性

"已安装"与"待上架"并列出现，只有一个成因：安装台账还在、磁盘包被删了。此时必须合成**单一状态**「包缺失 · 待重新入库」，并在详情页说明成因与恢复路径（重新上传同一 `appId` 的包并通过审核即可，账号安装记录不用重做）。不许把两个互斥标签并排放给用户。

### 5.6 应用版本演进（更新 / 回滚）

应用与技能的最大差别：**它是本机长活进程，还压着用户正在处理的数据**。所以版本变更不能只靠"发布即生效"。

**三处版本必须分开报，不许合成一个 `version`：**

| 字段 | 含义 | 来源 |
| --- | --- | --- |
| `marketVersion` | 市场条目审核通过的版本（最新可用） | 市场条目 `version` |
| `installedVersion` | 磁盘 `current.json` 指向的版本（装的是什么） | `currentAppInfo()` |
| `runningVersion` | 运行中进程实际加载的版本（跑的是什么） | `runtime.json` 的 `version` |

三者不一致就是事故现场：`installedVersion > runningVersion` 说明切了版本但旧进程没退（界面显示已更新、实际还在跑旧代码）；`marketVersion > installedVersion` 说明有更新未应用，详情页必须给出显式入口。

**【硬】切换版本必须一并回收旧进程。** `switchAppVersion()` 里除了改 `current.json`，还要 `killTree(pid)` + `APP_SECRETS.delete` + `leaseSet.clear()` + 写 `runtime.status=stopped` 并留下可解释的 `lastError`。只改指针不杀进程，用户会得到"更新成功但行为没变"的假象，这是最难排查的一类不一致。

**发布策略：照 App Store 的语义——上架不等于替用户换版本。**
- 审核通过只把新版本写进 `versions/<ver>`，**不改已安装用户正在用的 `current.json`**；只有本机还没有可用当前版本（首次入库，或 `current.json` 指向的目录已丢失）时才直接指向新版本；
- 因此"市场发了新版、本机还在跑旧版"是一个**正常可见状态**（`versionDrift`），而不是需要消灭的异常；
- 更新与回滚是同一个动作——切 `current.json` 指向，区别只是目标取"市场最新"还是"本机旧版本"；
- 应用页必须有入口：导航「应用」带可更新数量角标，工具栏「更新」按钮打开更新面板（列 `v旧 → v新`、是否正在运行中），支持单项更新与「全部更新」；无更新时面板显示"都是最新版本"，入口常驻；
- 详情抽屉同时提供「更新到 vX」（`versionDrift` 为真时）与「切换到此版本」下拉（`versionDirs` 任选，即回滚），并在"已切到新版但进程还是旧的"时给出「重启后生效」提示；
- 安装台账 `installRecords[].version` 记录"他最初装的是哪个版本"，包被新版本替换后这是唯一的溯源依据。

**权限：按用户，不按管理员身份。** 只有**安装过该应用的账号**能更新或切换版本（`AS_NOT_INSTALLED` 403）；管理员身份不构成代他人切版本的理由——应用是机器级单例，谁用谁负责。`as/start` 仍保留管理员可启动的例外（排障需要），但 `as/version` 不放宽。

**接口约定**：`POST /api/as/version`，body `{ id: 市场条目ID, version?: 目标版本（缺省为市场最新） }`；目标版本不在 `appVersionList()` 时返回 409 `AS_VERSION_MISSING` 并回传 `versions` 列表；成功记审计 `as.version`。

**版本目录只增不删。** `versions/` 是回滚的唯一依靠，只有 5.4 的整包移除才动它。账号数据在 `users/<账号>/` 下，不随版本走，所以回滚不会丢项目。

**版本号口径（v1.0.9 起强制）：`主.次`，从 `1.0` 起步。** 不写 `0.x`——`0.x` 让人以为还没成形；小改动进次位（`1.0 → 1.1 → 1.2`），不兼容或大改才动主位（`2.0`）。补丁位只有确实需要三级时才加，不默认写 `x.y.z`。`app.json.version`、市场条目版本、`versions/` 目录名必须是同一个字符串，界面统一加 `v` 前缀显示。

**「可更新」标签本身就是更新按钮。** 列表卡片与左侧已安装项上的 `可更新 vX` 是按钮而非装饰：点一下直接按当前账号切到市场最新版本（`quickUpdateApp()` → `POST /api/as/version`），与抽屉里「更新到 vX」共用同一条链路，同样会回收旧进程、重拉市场。要退回旧版本仍走抽屉的版本下拉，列表上不提供回滚。

**抽屉不得盖住最上层工具条。** `#slide` 打开时按 `.topbar` 的实际高度把 `top` 往下让（`slideTopOffset()`），顶部栏不存在或已隐藏时退回 0。写死像素会在不同布局下错位。

**验证要求**：改这条链路必须实测"回滚 → 启动（确认 `runtime.version`）→ 切回最新（确认旧进程被停）→ 非法版本返回 409"四步，只测其中一步不算通过。

### 5.7 应用托管模型（模型只能从中枢选）

**原则：应用不持有模型密钥，只认中枢下发的清单和短期令牌。** 应用里再出现"本机模型配置"就等于把密钥散落在用户机器上，也让同一份应用在不同账号下行为不一致。因此托管模式下必须做到三点：

1. **清单由中枢下发。** `GET /api/as/models?appId=&contextToken=` 返回 `{managed, baseURL, token, models:[{kind,name,model,modelLabel}]}`，`kind` 覆盖 `recognition / discovery / reconstruction`。选模型的口径是"有真凭据"优先：图像模型先挑自带 `apiKey` 的记录，再退到内置 provider；只登记了密钥环境变量而变量为空的预设，属于"列得出、调不通"，不能作为下发项。
2. **调用只走回环代理。** `POST /api/as/v1/chat/completions`、`POST /api/as/v1/images/edit` 用 Bearer 应用令牌验签后，由中枢代取密钥调用上游。应用侧只拿到 `http://127.0.0.1:<port>/api/as/v1` 这个地址。
3. **本机清单要让位。** 工作台读到中枢描述文件（`MATERIAL_STUDIO_HUB_MODELS`）后，候选模型只保留中枢行，本机管理中心的新增/编辑/删除一律 403，前端三处下拉统一置灰并显示中枢模型名，不再出现"本机环境"字样。

**令牌生命周期**：`mintAppModelToken` 走应用进程的 `APP_SECRETS`，有效期 30 天；应用进程重启或换账号会轮换密钥，旧令牌全部失效。所以**每次启动应用都要重新拉一次清单并重写描述文件**，工作台只在启动时读它——描述文件写晚了，进程里就是过期令牌。令牌失效就返 401 `AS_CONTEXT_INVALID`，应用应提示"重新打开应用"，不做自动重试。

**百炼系图像模型必须走原生多模态接口。** OpenAI 兼容的 `images/generations` 只认文生图，参考图会被丢弃；带参考图的材质贴图重建要打 `${origin}/api/v1/services/aigc/multimodal-generation/generation`，再从返回的 OSS 地址下载后转 `b64_json`。

**验证要求**：改这条链路必须同时实测「清单三类齐全」「chat 能返回内容」「images/edit 返回 1024×1024 PNG」「本机模型不出现在候选里」四项。

## 6. 应用工作区（WebContentsPane）规范

### 6.1 【硬】bounds 时序：容器先行必须补推

`browser:bounds` 在主进程里遇到"视图还没创建"时会丢弃矩形。而"先挂容器、再等进程"的设计必然让 bounds 早于 `browser.open` 到达，结果视图以默认 0 尺寸出现——症状就是**条带在、内容全白**，而日志里后端全是 200。

两条同时做，缺一不可：

```js
// 主进程：记住最近一次矩形，建视图时立刻应用
let browserBounds = null
ipcMain.on('browser:bounds', (_e, rect) => { browserBounds = {...}; if (!browserView || !browserAttached) return; browserView.setBounds(browserBounds) })
if (browserBounds) browserView.setBounds(browserBounds)   // ensureBrowserView 内

// 前端：open 之后再补推一次
window.jgClient.browser.open(url)
requestAnimationFrame(() => sendNativeBounds('asWebSlot'))
```

### 6.2 原生视图与 DOM 的层级

`WebContentsView` 永远压在 DOM 之上。任何要盖住工作区的 DOM 浮层（详情抽屉、确认框）都必须先 `hideAsPane()`，否则只露出条带一条缝。反过来，工作区打开时触发 `renderView()` 要保证不会因为视图切换把 DOM 重新盖上去——`renderView()` 开头已有互斥判断，新增页面必须复用，不许另写一套。

### 6.3 条带文案

- 条带三段固定：`#asPaneTitle`（应用名）/ `#asPaneOrigin`（实际 origin）/ 操作按钮（停止应用、退出应用界面）。
- 启动期间 origin 显示「正在启动…」，拿到 url 后立刻替换为真实 origin——**这是"到底卡在哪一段"的唯一可视化线索**，不要省。
- 【硬】条带**不显示 `asUser`**。账号标识不进 UI，避免截屏外泄；需要排查时走日志与审计。

## 7. 提交与验证门槛

### 7.1 【硬】改动类型 → 必须完成的验证

| 改动 | 必须做 | 禁止 |
| --- | --- | --- |
| `public/app.js` | `node --check` + bump `app.js?v=` + 说明影响页面 | 只改文件不 bump 版本 |
| `server.mjs` | `node --check` + 列出受影响路由 + 说明持久化字段 | 直接改 `jg.sqlite` 绕开 API |
| `as-runtime.mjs` | `node --check` + 用一次性目录验证（如 `data/apps/zz-verify-*`，测完删除） | 在真实应用目录上试破坏性操作 |
| `electron/main.cjs` | `node --check` + **明确告知需要重启客户端**（前端刷新无效） | 改完让用户"刷新页面" |
| 应用包 | 重新打包 → 重新入库 → 源码与包内文件哈希比对一致 → 冷启动实测 | 就地改 `data/apps` 里的文件 |
| 新增/更新应用包（AI 接入） | 按 §3.7 四项验收：`app_list`/`capability_list` 可见、`app_call` 真实 2xx、`app_data_list`/`read`/`query` 回读、越界与密钥拒绝 | 只改 `app.json` 不验接口；只验一个工具就宣称“全部接入” |
| 涉及生命周期的修复 | 给出审计表时序（`as.start`/`as.stop`/`plugin-market.delete`）+ `runtime.json` 对账 | 只看 UI 现象就下结论 |

### 7.2 结论纪律

- 修复必须能回答"为什么是这个原因"，而不是"改了以后好像好了"。能用的证据形态：审计表时序、`runtime.json` 状态与时间戳、应用侧 `runtime.log` 的请求行、独立进程复现（起进程 → 探活 → 观察存活时长）。
- 【硬】**未做运行时验证的修复必须显式标注"已落地未验证"**。本轮两次修复（bounds、互斥释放租约）就是先落代码、后验证，中间客户端的关闭状态要说清楚，不能让读者误以为已验证。
- 规范本身也要跟着改：每修一个"下次一定还会犯"的坑，就往 `as-poc/README.md` 或本文件补一条硬性条款，并写清验收口径与实测数字。

## 附录 B：术语

| 术语 | 含义 |
| --- | --- |
| AS Runtime | Application Shell Runtime，应用进程的托管层（`as-runtime.mjs`） |
| 租约（lease） | 前端视图占用计数，心跳续期；常驻模式下只反映"当前是否有界面连着"，不决定进程生死 |
| 应用工作区 | `#asPane` + 原生 `WebContentsView` 组成的容器，中枢充当操作系统 |
| `asContext` | 携带 `appId`/`userId`/`exp`/`nonce` 的签名票据 |
| 条目（market item） | 应用市场里的一条记录，`id` 形如 `M-<ts>`，与物理包不是一回事 |
| 包缺失 | 安装台账还在、磁盘包没了；唯一合法成因是"同 appId 的其它条目被删" |
