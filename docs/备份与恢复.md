# 备份与恢复

## 现状

- 服务启动时先做一次「启动备份」，运行期间按 `JG_BACKUP_INTERVAL_MIN`（默认 10 分钟）做一次一致性快照。
- 快照方式：`PRAGMA wal_checkpoint(FULL)` + `VACUUM INTO` 生成 `jg.sqlite`，同时整目录复制 `data/files`。
- 每个快照带 `manifest.json`，记录 `fileCount`（未删除文件数）、`auditCount`、`sessionCount`、`dbBytes`，用于恢复后校验。
- 保留策略（`db.mjs` 的 `pruneBackupsTiered`）：
  - 最近 `JG_BACKUP_KEEP_RECENT`（默认 12）份全留；
  - 再往前 `JG_BACKUP_HOURLY_HOURS`（默认 24）小时内每小时留 1 份；
  - 再往前 `JG_BACKUP_DAILY_DAYS`（默认 7）天内每天留 1 份；
  - 其余删除；非时间戳目录（人工放置的快照）不参与裁剪。

按默认值、10 分钟间隔估算：约 12 + 24 + 7 ≈ 43 份、当前数据量下约 2.6 GB。磁盘更紧张时可把 `JG_BACKUP_INTERVAL_MIN` 调到 15–30，或调小上述三个保留参数。

## 恢复工具

`scripts/restore-backup.mjs`，只用 `node:sqlite` 只读校验，不改动源备份。

```powershell
# 列出全部备份
runtime\node.exe scripts\restore-backup.mjs --list

# 恢复到临时目录演练（推荐每次改动后跑一次）
runtime\node.exe scripts\restore-backup.mjs --backup latest --target data\_restore\drill-1 --force

# 用恢复出来的数据目录启动一个旁路实例验证
$env:JG_DATA_DIR='D:\project-test3\jg-client-1.0\data\_restore\drill-1'
$env:PORT='54271'
runtime\node.exe server.mjs
```

校验项：`quick_check=ok`、`files`（未删除）、`audit`、`sessions` 与 manifest 一致，且每条未删除文件记录的 `path` 在恢复目录里真实存在（artifact 缺失数必须为 0）。

## 生产恢复步骤（会覆盖当前数据）

1. 停止服务进程（确认 `server.mjs` 已退出，`jg.sqlite-wal` 不再增长）。
2. 先复制当前 `data/jg.sqlite` 与 `data/files` 到另行存放的目录，保留回退点。
3. 执行：
   ```powershell
   runtime\node.exe scripts\restore-backup.mjs --backup <备份ID> --target data --force
   ```
4. 启动服务，检查 `/api/health`、登录、图像版本列表与最近会话是否可见。
5. 检查 `.workperf.err.log` 是否为空。

脚本会在覆盖前试打开目标库：若被占用会直接报「服务可能仍在运行」，不会盲写。

## 已知边界

- **恢复窗口取决于保留策略**，不是无限；跨机器/跨盘灾备仍需另行把 `data/backups` 同步出去。
- 每次快照整目录复制 `data/files`，写放大明显（当前约 60 MB/次）；数据量增长后应改为增量或对象存储快照。
- 恢复演练只验证了「库 + 文件产物」可读可启动，未验证跨版本迁移（旧库结构 → 新代码）场景。
