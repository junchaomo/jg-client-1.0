# AI 图片生成模块最小改造方案

日期：2026-11-15  
适用范围：`D:\project-test3\jg-client-1.0`

## 一、结论

采用“现有模型配置与凭据 + 图片 Provider 适配器 + Image Service + 图片页/Agent 工具”的垂直切片，不先建设通用多模态网关。

首期只解决图片能力，达到以下可验收结果：

- 接入至少一个真实生产图像 Provider，Pollinations 仅保留为测试通道。
- 图片任务异步执行，支持状态查询、失败重试和取消。
- 最近生成的真实作品可跨刷新恢复，不再只存在 `state.imagegen.shots` 内存中。
- 图片页只展示“最近生成”，不出现热门、模板、示例卡片或演示数据。
- 每张图片右上角提供横向三点菜单；菜单中的“编辑”创建新的真实修订版本，旧版本保留。
- 保留现有聊天、工作区、Visual Engine 和文件存储，不做破坏性重构。

明确不在首期建设：

- 视频、音频等通用多模态模型网关。
- 完整的成本中心、配额矩阵、自动模型评分和复杂路由算法。
- Photoshop 式图层/选区编辑器。
- 任意 HTML/React 图像应用沙盒。
- 任何形式的本地假画面、示例图或演示回退。

## 二、当前仓库事实与缺口

### 2.1 已有能力

| 位置 | 当前事实 |
| --- | --- |
| `server.mjs` | `IMAGE_GENERATION` 由环境变量配置；`POST /api/images/generate` 同步调用外部服务；`GET /api/images/file?id=` 读取落盘文件。 |
| `db.mjs` | `files` 保存当前文件元数据；`file_versions` 保存每次二进制版本；`putFile()` 对同一 `id` 再次写入会自动升版本并保留旧版本。 |
| `public/app.js` | `renderImage()` 当前只渲染 `state.imagegen.shots`；无服务端历史列表；无三点菜单；点击卡片直接打开结果弹窗。 |
| `model.mjs` | 只处理聊天模型配置与 Chat Completions，不负责图像 Provider；不能直接把图像配置混入 Chat 模型配置。 |
| `public/app.js` 菜单 | 已有 `.conv-menu` 弹出菜单模式和 `openModal()` 弹窗，可复用；不另造一套菜单组件。 |
| 已提交 `a181859` | 已删除 `IG_PRESETS`、`paintShot`、`igPresetArt` 等假数据和 `public/ig/*.jpg`，图片页已有真实空状态。 |

### 2.2 关键缺口

1. `POST /api/images/generate` 是同步长请求，没有 `ImageTask` 状态、排队、重试、取消。
2. 没有图片资源列表接口，刷新页面后无法显示真实最近生成。
3. 没有编辑接口、版本记录和恢复接口。
4. 图片 Provider 固定为 Pollinations 风格端点，无法按 Provider 声明生成/编辑/参考图能力。
5. 图片页没有三点菜单，无法从最近生成直接进入编辑。
6. 缺少图片任务与资产的权限、审计和网络域校验的完整闭环。

## 三、目标结构

```text
Harness 页面 / Agent 工具
        │
        ▼
Image Service（任务、最近作品、编辑、版本、权限、审计）
        │
        ▼
Image Provider Registry（生成 / 编辑 / 参考图能力）
        │
        ▼
企业图像模型（首期一个生产 Provider；Pollinations 仅测试）
```

### 3.1 对现有架构的边界

- `model.mjs` 继续只负责聊天模型；不为了图片改造 Chat Completions。
- 新增 `image-providers.mjs` 负责图片 Provider 注册与调用适配。
- 新增 `image-service.mjs` 负责任务编排、资产、修订、最近列表和权限前置校验。
- `server.mjs` 只做 HTTP 路由、身份/网络上下文和响应，不把 Provider 细节塞进路由。
- `db.mjs` 增加图片业务表，但二进制仍走既有 `putFile/file_versions`。
- 图片页复用现有 `openModal()`、`.conv-menu`、布局与主题变量。

## 四、数据模型

### 4.1 `image_jobs`

一条生成或编辑任务。

| 字段 | 说明 |
| --- | --- |
| `id` | 任务 ID，例如 `IMJOB-...` |
| `mode` | `generate` / `edit` |
| `status` | `queued` / `running` / `succeeded` / `failed` / `cancelled` |
| `provider` | Provider ID，例如 `qwen-image` |
| `model` | 模型 ID |
| `prompt` | 用户原始提示词 |
| `ratio` | 图片比例 |
| `source_asset_id` | 编辑任务的原图资产，生成任务为空 |
| `owner` | 创建用户 |
| `net` | 创建时的网络域 |
| `error_code` | 失败错误码 |
| `error_message` | 失败原因 |
| `result_asset_id` | 成功后的资产 ID |
| `created_at` / `updated_at` | 时间戳 |

### 4.2 `image_assets`

一条逻辑图片作品。

| 字段 | 说明 |
| --- | --- |
| `id` | 资产 ID，与当前文件 `file_id` 对齐 |
| `file_id` | 文件存储 ID |
| `job_id` | 首次生成任务 |
| `title` | 展示标题，可自动取提示词摘要 |
| `current_version` | 当前修订版本 |
| `owner` / `net` | 归属与网络域 |
| `created_at` / `updated_at` / `deleted_at` | 生命周期 |

### 4.3 `image_revisions`

一条资产修订记录，与 `file_versions` 对齐。

| 字段 | 说明 |
| --- | --- |
| `asset_id` | 资产 ID |
| `version` | 修订号，从 1 开始 |
| `job_id` | 产生该版本的编辑/生成任务 |
| `prompt` | 该版本提示词 |
| `provider` / `model` | 实际服务 |
| `ratio` / `seed` | 生成参数 |
| `file_version` | 对应的 `file_versions.version` |
| `created_at` | 时间戳 |

### 4.4 存储原则

- 图片二进制统一走 `putFile`，不把 base64 存进业务表。
- `image_revisions` 只保存业务版本元数据；二进制由 `file_versions` 保存。
- 生成新图使用新 `image_assets.id`；编辑同一作品使用同一资产，`putFile` 升新版本，并写一条 `image_revisions`。
- 旧版本不得删除；恢复版本只切换当前版本，不覆盖历史。
- 删除采用软删除：`image_assets.deleted_at` 非空后不再进入最近列表，文件仍可按版本审计。

## 五、API 设计

### 5.1 新接口

| 方法与路径 | 作用 |
| --- | --- |
| `POST /api/images/tasks` | 创建生成/编辑任务，返回 `jobId`，不阻塞等待 |
| `GET /api/images/tasks/:id` | 查询任务状态、错误、结果资产 |
| `POST /api/images/tasks/:id/cancel` | 取消排队或运行中的任务 |
| `GET /api/images/recent?limit=24` | 当前用户最近生成的真实作品 |
| `GET /api/images/:assetId` | 资产详情、当前版本和参数 |
| `GET /api/images/:assetId/versions` | 版本列表 |
| `POST /api/images/:assetId/edit` | 基于原图创建编辑任务 |
| `POST /api/images/:assetId/restore` | 恢复某个历史版本，生成新的当前版本 |
| `DELETE /api/images/:assetId` | 软删除作品 |

### 5.2 兼容策略

- 保留 `POST /api/images/generate`，作为 `POST /api/images/tasks` 的兼容包装；旧页面或旧工具不必立即迁移。
- 保留 `GET /api/images/file?id=`，不改读取路径与权限校验。
- 最近列表只返回 `status=succeeded`、`deleted_at IS NULL` 的资产，按 `updated_at DESC` 排序。
- 任务状态首期由前端轮询；不引入消息队列和 SSE，单机进程内 worker 足够。

### 5.3 任务执行

1. 路由层创建 `image_jobs`，状态 `queued`。
2. Image Service 进程内 worker 取任务，状态改 `running`。
3. 调用 Provider Adapter，校验返回 MIME、尺寸、大小。
4. 成功后 `putFile` 落盘，写 `image_assets` / `image_revisions`，状态 `succeeded`。
5. 失败写错误码和可读原因，状态 `failed`；不自动用本地假图兜底。
6. 取消只对 `queued`/`running` 生效；已提交到外部服务的请求不能被本地取消时，明确返回“已提交，无法撤回”，不伪造取消成功。

## 六、Provider 适配器

### 6.1 接口

```js
provider.capabilities = {
  generate: true,
  edit: false,
  referenceImage: false,
}
provider.generate({ prompt, ratio, style, seed, signal })
provider.edit({ prompt, ratio, sourceBuffer, sourceMime, signal })
provider.health()
```

适配器只做参数转换、鉴权、调用和响应归一化，不承担页面状态和业务权限。

### 6.2 首期 Provider 策略

- 首期只接一个已采购、可用的生产 Provider；优先选择同时支持生成和编辑的企业模型。
- 若 Qwen-Image 3.0 的生成/编辑接口和企业凭据已可用，可作为默认 Provider。
- 若 Qwen 编辑能力不可用，则生成用 Qwen，专业编辑用 Seedream 5.5；两家都通过同一 Adapter 接口接入。
- Pollinations 保留 `pollinations` Adapter，仅用于开发/连通性测试，不作为默认生产模型。
- Provider 的 API Key 只在服务端配置，浏览器和前端请求体都不能携带第三方 Key。
- Provider 不支持编辑时，前端三点菜单的“编辑”置灰并显示原因，不伪造编辑能力。

### 6.3 响应归一化

Provider 必须返回：

```js
{
  buffer: Buffer,
  mime: 'image/png' | 'image/jpeg' | 'image/webp',
  width: Number,
  height: Number,
  provider: String,
  model: String,
  requestId: String,
}
```

服务端拒绝非图片 MIME、空文件、过小文件、超大文件和无法解析的尺寸。

## 七、图片页交互

### 7.1 页面结构

```text
图像
最近生成                                  [刷新]
┌──────────────┐ ┌──────────────┐
│ 真实图片      │ │ 真实图片      │
│ 提示词摘要    │ │ 提示词摘要    │
│ 参数          │ │ 参数          │
│           ⋯  │ │           ⋯  │
└──────────────┘ └──────────────┘

[描述新图像                        生成 ↑]
```

- 不设“热门 / 模板”tab。
- 不展示任何示例卡片或占位图。
- 空状态保持当前文案；首次生成后从 `GET /api/images/recent` 重新拉取。
- 页面加载显示轻量骨架或“加载最近作品”，不先渲染假卡片。

### 7.2 三点菜单

每张卡片右上角提供 `⋯` 按钮，使用现有 `.conv-menu` 弹出菜单，至少包含：

| 菜单项 | 行为 |
| --- | --- |
| 编辑这张图 | 打开编辑浮窗；Provider 不支持编辑时置灰并说明原因 |
| 下载原图 | 下载当前版本文件 |
| 用于会话 | 上传到聊天附件，复用现有 `uploadBinaryFile` 逻辑 |
| 查看版本 | 打开版本列表与恢复入口 |
| 删除 | 二次确认后软删除，从最近列表移除 |

实现时必须把当前 `.img-card` 外层从单个 `<button>` 改为非交互容器（如 `article`/`div`），图片预览和三点菜单分别作为两个独立按钮，避免按钮嵌套按钮导致键盘和触控行为异常。菜单按钮必须 `stopPropagation`，避免点击菜单时打开预览。键盘焦点、移动端触控和窄屏布局沿用现有菜单规范。

### 7.3 编辑浮窗

首版不做画布式编辑器，只做“自然语言编辑”：

- 左侧或上方展示原图。
- 输入编辑描述，例如“把立面材质改成浅灰色石材，保留玻璃幕墙”。
- 展示当前 Provider/模型、比例、版本号。
- 提交后创建编辑任务，完成后在原作品上生成新版本。
- 提供“查看版本 / 恢复此版本”；旧版本始终保留。
- 编辑请求必须显式提示“参考图与提示词会发送到外部图像服务”，并受网络域与权限校验。

## 八、权限、安全与三网策略

- 继续使用 `imageGenerationStatus()` 的网络域判断：只有允许的网络域可以外发提示词/参考图。
- 生成和编辑前都校验资产归属：只允许 `owner` 本人访问；跨用户访问返回 403。
- 外部参考图必须先通过 `fileVisibleToUser()`，不能接受任意 URL 或前端传入的本地路径。
- API Key 只在服务端 Provider 配置中；日志、错误、前端响应都不能回显 Key。
- 每个用户限制并发任务数、每日生成数、单图大小、参考图数量；首期可用服务端常量配置，后续再进管理中心。
- 审计记录 `image.task.create`、`image.task.finish`、`image.edit`、`image.delete`、`image.restore`，包含用户、网络域、任务/资产 ID、Provider/模型和结果状态。
- 政务网/涉密网默认禁用公共云图像服务；如启用本地模型，Provider 必须走内网地址并单独登记。
- 删除只做软删除，避免误删原始作品；物理清理由管理员后续维护任务处理。

## 九、与 Agent、Visual Engine 的边界

- Visual Engine 继续负责 Mermaid、ECharts、SVG、声明式交互组件；不接管像素图片。
- Image Service 负责真实图像生成/编辑、任务、版本和资产。
- Agent 工具首批只注册 `image_generate` 与 `image_edit`；工具返回任务 ID 或资产 ID，不返回大段 base64。
- 聊天消息中展示真实图片卡片，支持打开预览、继续编辑、下载；不把图片任务塞进 Visual Engine 的 `visual_*` 工具。
- 聊天模型仍走 `model.mjs`；图片模型走 Provider Registry，两者通过“统一模型管理”逐步收敛，但首期不强行合并调用链。

## 十一、实施顺序与验收

### P0：接入可行性

- 确认首期生产 Provider、API 文档、企业凭据、计费方式和网络域可用性。
- 用一个真实提示词跑通生成，确认返回格式、耗时、失败码和图片质量。
- 不写前端假数据；失败时只展示真实错误。

验收：服务端能直接调用 Provider 并落盘一张真实图片；审计有记录。

### P1：Image Service 与持久化

- 建表、任务状态机、最近列表、编辑/版本/恢复接口。
- 兼容旧 `/api/images/generate`。
- 刷新页面后最近列表仍返回真实作品。

验收：生成一张图，刷新后仍能在最近列表看到；服务端重启后仍能读回。

### P2：图片页

- 移除 `state.imagegen.shots` 作为唯一数据源，改为 `GET /api/images/recent`。
- 只保留“最近生成”区域；无热门、模板、示例图。
- 卡片右上角三点菜单；编辑、下载、用于会话、版本、删除。
- 窄屏与触控可用；菜单可键盘关闭；图片加载失败有恢复提示。

验收：
- 空状态不出现任何示例卡片。
- 生成后卡片来自真实接口。
- 三点菜单能打开编辑浮窗；Provider 不支持编辑时明确置灰。
- 编辑成功后出现新版本，旧版本可恢复。

### P3：Agent 工具与第二家 Provider

- 注册 `image_generate`、`image_edit`。
- 第二家 Provider 只用于证明 Adapter 抽象，不先做自动路由评分。
- 管理中心只提供最小 Provider 配置/启停，不做完整成本中心。

验收：聊天中可生成并展示真实图片；第二家 Provider 切换后业务逻辑不变。

## 十三、进入实现前需要确认的事项

1. **首期生产 Provider**：Qwen-Image 3.0 是否已开通生成与编辑接口；若没有，是否先以 Seedream 5.5 作为编辑位。
2. **编辑语义**：首版是否只做“自然语言指令编辑”，还是同时支持参考图/多图融合；本方案默认只做单图自然语言编辑。
3. **删除策略**：默认软删除并从最近列表移除；是否需要“彻底删除”入口另行确认。
4. **管理入口**：首期 Provider 配置放在服务端环境变量/管理配置，还是同时在管理中心做可视化表单；本方案默认先服务端配置，管理中心只读展示。
5. **个人 Key**：是否允许员工自带图像 API Key；本方案默认只允许企业统一 Key，个人 Key 后置评估。

## 十四、明确不做

- 不恢复“热门 / 模板”入口。
- 不恢复任何示例图片、示例卡片、假画面生成器或演示控件。
- 不把图片任务并入 Visual Engine。
- 不首期建设通用视频/音频网关。
- 不首期实现 Photoshop 式图层/选区编辑。
- 不以自动模型评分替代人工配置；首期使用明确默认 Provider。
