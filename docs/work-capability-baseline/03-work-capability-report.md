## 三、本轮修复的两个真实缺陷

**1. 模型输出截断被误判为完成。** 首次代码核验任务输出 20950 tokens，`finishReason=max-tokens`，任务却被写成 `done`。修复后新增 `interrupted` 状态：达到输出上限时保留执行记录和回复，但不再冒充完成。

**2. 中枢自身数据库变更被算成项目产物。** 第一次假完成任务的 `artifacts=1`，来源是 `data/jg.sqlite-wal`，不是用户成果。修复后按路径去重，并排除 `data/`、`node_modules/`、`.git/`、`runtime/`、`.dsh` 等运行时目录。

**真实压力验证**：修复后重新下发同一高消耗任务，运行 143.6 秒、58 次工具调用、18971 output tokens，最终 `state=interrupted`、`artifacts=0`，回复为“【未完成】本轮执行达到模型输出上限……可从执行记录恢复继续”。说明修复在真实运行中生效，不是只改文案。

## 五、能力边界

**已成立**

1. 单会话 Work 任务可创建、执行、落库、按会话定位，短任务完成率稳定。
2. 项目绑定代码路径已接通，本项目三条链已验证 `projectId` 归属与项目计数。
3. 完成/中断/取消三种结束状态有区分，产物计数不再把运行时文件算进去。
4. 中断任务保留恢复入口，前端有恢复按钮，恢复时明示不自动重放副作用。

**未成立或未验证**

1. 不能称“项目级平台已规模化”：历史 242 条 chat-run 的项目归属仍为 0，当前只有这一个基线项目。
2. 不能称“恢复已生产验证”：生产 `resumeState` 全空，本轮也未做恢复演练。
3. 不能称“并发已压测”：`MAX_CHAT_RUNS` 仍为 2，Chat 与 Work 共用进程级 FIFO 槽位，长任务会占满槽位。
4. 不能称“工作树隔离已验证”：项目绑定在仓库主工作区，`worktreePath` 为空，未验证 Git 隔离工作树。

## 六、剩余风险与下一步

1. **并发与排队策略（优先）**：保持默认 2，先做“2 个 Work + 1 个 Chat”的真实并发观测，确认 running/queued 与释放补位；是否提高上限要结合本机内存和 DSH 会话开销单独决策。
2. **恢复演练**：选一条 `interrupted` 任务发起恢复，验证返回 202、`resumeState=requesting`、同会话产生新任务，重复恢复返回 409，并确认没有副作用重放。
3. **工作树隔离**：为项目创建独立 worktree 后再跑一条写文件任务，确认源码工作区不被直接改动。
4. **pwsh 卡死根因**：Windows 下等待管道 EOF 的问题仍在，本轮通过只读工具和预计算数据绕过，尚未修复。

## 七、对外口径建议

可以表述为：“Work 单会话执行链已生产使用，项目绑定、成果计数和中断验收已在真实项目跑通。”  
不要表述为：“项目级并发平台已就绪”或“恢复、工作树已在生产验证”。
