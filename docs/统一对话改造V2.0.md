## 一、改造结果

- 取消 Chat / Work 一级模式切换，只保留一个 AI 对话入口。
- 项目 / 本地文件夹变为可选工作上下文，默认“项目或文件夹（无项目）”，不建项目也能直接聊天。
- 输入框下方新增两项控制：左侧项目 / 文件夹选择，右侧 Auto / Manual 执行权限。
- 删除前端 Default / Plan 开关，保留 Harness 原生 `/plan`。
- 会话是否属于项目由 `projectId` 推导，不再由前端 `mode` 决定。
- Auto / Manual 由服务端会话状态控制，并落到 Harness 原生沙箱权限预设，不只是提示词。

## 三、复用的 Harness 原生能力

- `Session.setWorkingDirectory(cwd)`：会话绑定真实执行目录。
- `resumeSession(savedId)`：重启后恢复会话历史。
- 原生 `/permission read-only|workspace-write`：权限预设，同时约束 sandbox 与 approval。
- `dsh-sandbox`：`read-only` 拒绝写入；`workspace-write` 仅允许工作区根目录写入。
- `dsh-user-approval`：被沙箱拒绝后，模型用 `sandbox_permissions` 升权重试，弹出一次性审批。
- 原生 `/plan`：保留计划模式；前端不设开关。
- `/api/chat/pending` / `approval` / `answer`：复用现有审批与提问通道。

## 四、状态与数据结构

会话对象新增 / 明确：

| 字段 | 说明 |
|---|---|
| `projectId` | 空表示普通聊天；非空表示绑定项目 |
| `mode` | 由服务端按 `projectId` 推导，仅供展示与兼容，不参与权限判断 |
| `executionPolicy` | `auto` / `manual`，服务端可信状态 |
| `agentCwd` | 实际执行目录；聊天为 `data\dsh-workspaces\chat\<userId>\<convId>`，项目为项目绑定目录 |
| `dshSessionId` | Harness 会话 ID，用于恢复 |

项目仍由企业中枢 `liveProjects` 持有：`id`、`name`、`cwd`、`folderName`、`deviceId`、`status`、`removed`。DSH 侧不另建平行项目表，只通过 `SessionHeader.cwd` 绑定目录。

## 五、本地执行链路

```
Electron 客户端
  → 本机 server.mjs（127.0.0.1 随机端口）
  → 本机 Harness 子进程（runtime\node.exe）
  → DSH Session（cwd = 项目目录）
  → 原生 sandbox / approval
  → 项目文件夹真实读写与 pwsh 执行
```

未通过服务器虚构 Windows 路径执行；文件读写由同机 Harness 子进程完成。

## 七、尚未完成 / 已知限制

1. **本地执行仅限同机**：当前是本机 Electron 起本地 server + 同机 Harness 子进程。没有设备配对、远程认证、断线暂停；`deviceId` 只是项目字段，未用于执行路由校验。
2. **跨用户隔离只覆盖聊天托管目录**：聊天目录按 `<userId>/<convId>` 隔离；项目目录是管理员为当前机器绑定的真实目录，未做多用户目录 ACL 隔离。
3. **Auto 的高风险审批不完整**：`workspace-write` 只强制“目录外写入”升权审批；目录内大规模删除、批量覆盖仍会被允许，需要后续在工具层加风险规则。生产库、对外发送等属于目录外/插件操作，现有沙箱只能部分覆盖。
4. **Manual 的审批是“被拒后升权”模式**：依赖模型在被 `read-only` 拒绝后按 Harness 提示重试；若模型不重试，操作不会执行（安全，但体验可能多一轮）。没有持久授权，也没有 allow-always。
5. **`/plan` 评审卡未在本次触发**：原生 `/plan` 可运行且模型遵守计划口吻，但模型未调用 `exit_plan_mode`，因此未验证计划评审 UI。计划状态与 Auto/Manual 已分离。
6. **`/api/harness/file` 仍只允许 `data\dsh-workspace`**：项目文件的预览/下载没有按项目 `cwd` 开白名单，当前只通过 Agent 工具读写，未打通产品文件预览。
7. **项目无 cwd 的旧数据**：`PRJ-01` 仍存在但不出现在可选项目列表；不会阻挡聊天。
8. **历史会话状态残留**：旧测试会话 `C-1794383686606`、`C-1794384235760` 仍显示 `running`，属于旧持久化数据，未批量清理。
9. **未做企业级审计落库**：工具调用与审批有会话内记录，但没有独立审计表/导出。
10. **未做远程 Desktop Host**：官方 DSH 桌面宿主不在此部署包内，本轮采用本机宿主适配，不是官方 Desktop Host 复用。

## 八、对上游升级的影响

- 依赖 Harness 原生 `/permission <preset>` 名称（`read-only`、`workspace-write`）与 `Session.setWorkingDirectory`；升级若改命令名或预设表，需要同步改 `harness.mjs`。
- 依赖审批事件 `approval/request` 与提问事件形状；`dsh-user-approval` 仍是 ask/never、一次性授权词汇。
- 项目实体仍在企业中枢侧，不依赖 DSH workspace registry；升级不需要迁移项目表。
- `/plan` 采用“激活 + 普通请求”两次调用，规避 SDK 命令 steer 不返回轮次的问题；若上游修复该行为，可恢复单次 `/plan <message>`。
- 前端未改共享样式，升级 UI 时不受本轮样式定制影响。

## 九、2026-11-12 三模式补充（覆盖前文第 9、11、13 条）

- 输入框新增 `Auto / Chat / Work` 任务模式胶囊，默认 Auto；不再由“是否绑定项目”隐式决定 Chat / Work。
- `server.mjs` 新增 `resolveTaskMode()`：手动 Chat / Work 直接覆盖；Auto 用 `WORK_INTENT_PATTERNS` 规则识别文件、命令、数据处理、多步骤与代码块意图，命中升级 Work，否则 Chat。
- 三种模式共用同一会话 ID、消息历史、附件、`dshSessionId` 与项目上下文，不新增独立页面。
- Chat 模式下需要权限升级的工具调用统一返回 `rejected`，模型提示切换到 Work；Auto / Work 沿用 `autoApprovalAllowed()` 审批矩阵。
- 审批胶囊移入输入框内部“＋”右侧，改为无边框浅灰胶囊；点击打开「请求批准 / 帮我批准」菜单，用户选择后才切换。快捷行保留项目、推理强度，任务模式放在推理强度右侧。
- 界面文案统一中文化：任务模式为「自动 / 对话 / 工作」，审批为「请求批准 / 帮我批准」；设置中心与模型上下文同步使用中文用词。
- 第一阶段完成：Auto 规则路由、手动模式选择、统一会话、审批隔离。执行中动态切换、企业身份与执行环境隔离尚未实现。详细实测见 `Harness逐步落实记录.md` 第 23 节。
- 第三阶段首批完成：每次真实运行生成持久化 `chat-run` 执行记录；进程重启后未收尾任务标记「已中断」，可从执行记录回到原会话并回填原指令。仍是同步执行，常驻后台 worker、队列并发与自动续跑未实现。详见第 24 节。
