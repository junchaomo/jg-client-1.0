# 平台 AI 能力真实评估

- 评估日期：2026-11-17
- 评估对象：九规智能中枢当前工作区（`<项目根>`）
- 评估方式：只读代码核对 + 真实模型调用 + Harness 真实执行 + 产品 API/MCP 调用 + 数据库状态核对 + 既有产品会话记录复核
- 评估口径：
  - **已跑通**：从真实入口发起，拿到真实结果、状态或副作用，并有可复核证据。
  - **已落地未验证**：代码、工具或入口已经存在，但没有从 AI 对话或产品入口完成闭环，或当前缺少可用数据/配置。
  - **明确没有**：没有实现路径，或现有实现明确不支持。

## 一句话结论

平台已经不是“只有按钮、没有能力”的空壳：DeepSeek 对话、Harness 工具执行、应用业务调用、应用数据读取、图像生成与编辑、审批审计都有真实跑通的链路。

但它也还不是“所有应用、插件、技能都能被 AI 自主调用”的成熟生产力平台。当前真实水平是：**单账号、单模型、单任务、受控工具链可用；多模型、多应用组合、全量技能、长期记忆、可靠定时和生产级可观测性仍未达到。**

整体评分：**3.1 / 5**。作为可运行的中台底座是及格偏上；作为集团级、可无人值守的生产力平台仍是早期。

## 一、已经跑通的能力

### 1. 模型网关：DeepSeek 真实可用，图像双供应商有成功产物

代码事实：

- `SYSTEM_PRESETS` 注册 6 个平台公共模型：4 个 chat（DeepSeek V4.1 Flash、Qwen4-Max、Kimi K3.1 Pro、GLM 5.3 Flash）+ 2 个 image（Seedream 5.5、Qwen-Image 3.0 Pro）。
- `routeModel` 支持按 quick/retrieval 做成本降级，`deepThink` 固定 `deepseek-reasoner`，图片请求在模型不支持图像时回退 `deepseek-flash`。

本轮实测：

- 直接用管理员账号的 DeepSeek 账号 Key 调用 `chatCompletion`，模型 `deepseek-flash`，返回内容“可用”，耗时约 1.0 秒，usage 为 35 输入 + 35 输出 = 70 tokens。
- 图像任务库当前有 25 个 `completed` 记录，Seedream 与 Qwen 都有成功任务，说明图像生成/编辑不是空入口。

必须说清楚的缺口：

- 当前可核实的 chat Key 只有 DeepSeek（账号级）；Qwen/Kimi/GLM 在进程、用户、机器环境以及共享模型记录里都没有读到可用 Key。因此 6 个预设里，**DeepSeek chat + 2 个 image 可用，3 个 chat 预设当前不可用**。
- `MODEL_CAPABILITIES` 只有 4 个 DeepSeek 条目的能力/成本画像；Qwen/Kimi/GLM 没有画像，`routeModel` 的自动成本路由实际上只对 DeepSeek 生效。
- 没有跨供应商自动失败切换：选中模型失败后不会自动改走另一个模型，只会返回错误。
- `deepThink` 固定走 `deepseek-reasoner`，即使用户当前选的是 Qwen/Kimi/GLM，也不是“所选模型自己深度思考”。

### 2. Harness 执行：真实工具回合成立，但成本偏高

代码事实：

- `runAgent` 支持 `reasoningEffort`、工具调用预算、`workspace-write/read-only` 权限预设、plan 模式、session 恢复、cwd 绑定、subagent 通知、取消和每轮工具策略文件。
- `toolPolicy` 可按意图收窄工具面；Chat 与 Work 使用不同核心工具集。

本轮实测：

- 无工具冷启动探针：真实返回“Harness可用”，但耗时 **60.5 秒**，输入 **12,343 tokens**，输出 5 tokens。
- 带应用工具的回合：模型先调用 `mcp__jg__capability_list`，再调用 `mcp__jg__app_call`，返回“最近一次运行的车辆总数是 17 辆”；耗时 **10.3 秒**，3 次调用，输入 5,190 tokens，缓存读取 8,320 tokens，`finishReason=completed`。
- 这说明“模型自主选工具 → 调应用 → 汇总结果”这条链路是真实成立的，不是只有 HTTP 接口能通。

限制：

- 冷启动开销很大，不适合把每个普通问答都送进 Harness；轻量问答应继续走直连模型。
- Harness 的 10 秒级响应适合单步工具任务，不适合多应用、多轮规划的高频办公场景。
- 会话记录里 104 个会话有 3 个 `failed`（约 2.9%），其中包含一次天气问法；说明链路可用但并非零故障。
- 之前截图里的“只输出半句、光标一直闪”是真实发生过的；本轮没有在 UI 里重新复现同一个故障，因此只能记录为“曾发生、未闭环定位”。

### 3. 应用 / 插件 / 技能：三个应用都能调，但“全量技能”不成立

应用：

- 当前 `capability_list` 返回 3 个应用：`jg-material-studio`、`traffic-flow`、`as-python-sample`，全部 `declared:true`，每个至少 1 个工具。
- 实测 `app_call`：
  - `traffic-flow` 的 `traffic.latest_output`：HTTP 200，总行数 22，返回车辆总数 17、PCU 26.0。
  - `jg-material-studio` 的 `material_studio_status`：HTTP 200，工作台 `http://127.0.0.1:4173/`，dataDir 指向当前账号。
  - `as-python-sample` 的 `python.get_state`：HTTP 200，进程 PID 与账号 dataDir 正常返回。
- 新应用的机制已经落地：扫描 `data/apps` 真实安装态，声明 `capabilities.tools/resources` 的应用自动进入目录；未声明能力的应用只算“可发现/数据可读”，不算“业务可调用”。
- 但本轮没有新安装一个应用做端到端验证；所以“以后新装应用自动可用”是**机制已落地，新增路径未实测**。

插件：

- 目录中有 3 个：`M-CODEREVIEW`、`runtime:jg-spill-age`、`runtime:jg-tool-router`。
- 只有 `M-CODEREVIEW` 是 `callable:true`，映射到 `mcp__jg__code_review`。
- 两个 runtime 插件是 Harness 运行时扩展，`callable:false` 是设计边界，不应包装成对话工具。

代码审查的真实状态：

- `code_review` 工具已注册，但当前通过 MCP 身份调用 `P-REVIEW` 返回 403“当前身份无权审查该项目”；`/api/projects` 经 MCP token 调用返回 0（该路由不识别 MCP token，不能据此断言没有项目）。
- 结论只能写“工具已登记，未完成一次真实项目审查”，不能写“代码审查插件可用”。

技能：

- `capability_list` 只有 `agent-experience`、`cordis-plugin-development` 两个账号技能。
- 系统侧已安装的技能约 50 个，但没有被同步进中枢账号的技能根；平台 AI 运行时看不到它们。
- 因此，“所有技能都能被中枢 AI 调用”当前**明确不成立**；成立的是“账号技能目录中的 2 个技能可被发现，UI 端到端加载尚未验收”。

### 4. 应用数据：当前账号的文本与 SQLite 已跑通，AI 真实读到了交通输出

这是本轮最实的改造之一。

- `app_data_list` 返回 3 个应用、3 个文件：
  - `jg-material-studio`：`material/studio.sqlite`
  - `traffic-flow`：`data/history.json`、`outputs/7c478ad8_video_sections_events.csv`
  - `as-python-sample`：当前 0 个文件
- 真实产品会话（标题“查看交通流量应用输出数据”）中，助手实际执行了 `app_data_list` + 两次 `app_data_read`，回答出了运行 ID、运行时间和输出概览。这证明不是工具接口自嗨，AI 对话确实读到了应用生成数据。
- `app_data_query` 对 `material/studio.sqlite` 执行只读查询成功，能列出 30 个 SQLite 对象；`delete from materials` 返回 `AS_APP_DATA_SQL`；跨账号路径返回 `AS_APP_DATA_PATH`。
- 文本读取限制 512KB，单文件上限 8MB，只支持文本扩展名；二进制产物需要应用自己声明工具。

边界：

- 数据严格按当前账号隔离，跨账号读取被有意拒绝；如果用户要“所有账号的生成数据”，当前没有授权模型。
- `materials` 当前 0 行，`models` 2 行；材质库只证明了表结构和查询通道，没有证明“有真实材质数据时的读取效果”。
- 图片、视频、Office 等二进制文件没有通用解析通道。

### 5. 图像、可视化、语音：有真实产物，语音还缺端到端验收

- 图像：25 个 `completed` 图像任务，覆盖 Seedream 与 Qwen，包含生成、编辑、局部重绘等真实提示词；两个图像 Key 当前有值。
- 可视化：`visual_artifacts` 10 条；支持 mermaid、echarts、svg、interactive 四种类型，有服务端校验和存储。
- 语音：
  - 本地离线识别 SenseVoiceSmall 已就绪，模型 `model.int8.onnx`，约 241MB，支持 auto/zh/en/yue/ja/ko。
  - 本地 TTS Piper 文件存在，中文模型 `zh_CN-huayan-medium.onnx` 约 63MB，`data/tts-cache` 已存在。
  - 但本轮没有做一次“录音 → 转写 → 模型回答 → 语音播报”的 UI 闭环，因此只能算“模型与接口就绪，端到端未验收”。
- 图像输入理解、视频理解当前没有实测证据；不能因为存在图像生成就宣称“多模态对话完整”。

### 6. 权限、审批、审计：边界是真实存在的

- `approval_decisions` 当前 39 条：allowed 9、deny 15、rejected 6、expired 5、cancelled 4。
- `audit` 3,763 条，说明工具调用、审批、配置等操作有持续记录。
- Harness 支持 `read-only` 与 `workspace-write` 权限预设；外部副作用工具（IM、任务创建、上传/发布等）有专门规则，不会在 Auto 模式无条件放行。
- 代码审查返回 403，反而说明权限边界不是装饰：没有项目权限就是不能审查。

限制：

- 组织级、跨部门、跨账号的细粒度授权没有完整验收。
- 审批 UI 的交互质量、批量审批、审批历史导出没有在本轮评估。

### 7. 可观测性：有每轮轨迹和用量，但没有生产级观测

- AI 回合会返回 `steps`、`usage`、工具审计和 `finishReason`；应用工具回合能看到模型网关、`capability_list`、`app_call` 三步。
- 数据侧有 3,763 条审计、25 个图像任务、10 个可视化产物、118 个文件。
- 但目前没有：
  - 按模型/工具/租户的聚合成功率、P50/P95 延迟、错误码分布；
  - 生产 SLO、告警、成本预算看板；
  - 长期评测集与回归门禁。

## 三、明确没有或不成立的能力

1. **“所有技能都能被中枢 AI 调用”不成立。** 中枢目录只有 2 个账号技能，系统侧约 50 个技能没有进入平台运行时。
2. **“所有应用数据都能被 AI 读取”不成立。** 当前只支持当前账号、文本和 SQLite；二进制没有通用通道，跨账号明确拒绝。
3. **“新装应用一定业务可调用”不成立。** 只有声明 `capabilities` 的应用才可业务调用；未声明只能发现和数据读取。
4. **“定时任务创建可靠”不成立。** 当前任务库 0 条、调度文件为空，历史截图出现过 AI 声称创建但页面为空的情况。
5. **“多模型自动路由/自动降级”不成立。** 只有 DeepSeek 有能力和成本画像；没有跨供应商失败切换。
6. **“长期记忆已生效”不成立。** 当前没有 active 记忆，只有 archived 测试数据。
7. **“生产级可观测性”不成立。** 有审计和单轮 steps，但没有聚合指标、SLO、告警和评测体系。

## 四、真实水平判断

### 可以承诺的场景

- 单账号日常问答：DeepSeek 直连约 1 秒，可用。
- 单应用读取：AI 能自主调用 `capability_list` + `app_call`，拿到交通应用真实结果。
- 单应用数据读取：AI 能自主调用 `app_data_list` + `app_data_read`，读出 CSV 和历史记录。
- SQLite 只读查询：能列出表、执行 SELECT，并拒绝 DELETE 与跨账号路径。
- 图像生成/编辑：Seedream 与 Qwen 都有真实成功产物。
- 可视化：mermaid / echarts / svg / interactive 有真实产物。
- 受控工具执行：有审批、审计、只读/工作区写权限预设。

### 不能承诺的场景

- 所有应用、插件、技能开箱即用。
- 多应用组合的自主多步任务。
- 跨账号/跨部门数据读取。
- 图片、视频、Office 文件的通用理解。
- 可靠定时任务和无人值守运行。
- 多模型自动容灾与成本最优路由。
- 生产级 SLA、全链路追踪和长期效果评估。

## 五、建议的优先级

### P0：先把“声称已支持”变成“可验收”

1. **技能目录统一**：把系统侧技能同步进中枢账号技能根，或在 `capability_list` 中显式区分“平台技能/账号技能”；否则“所有技能可调用”永远不成立。
2. **定时任务闭环**：用真实 UI 完成一次“创建 → 出现在任务页 → 到点触发 → 可暂停/删除”，并修正 `automationTick` 只同步已有 `source:'dsh'` 任务导致新任务不被发现的问题。
3. **代码审查验收**：给一个真实项目、真实 `cwd`、真实权限，跑通一次 `code_review`；否则只能标“已登记”。

### P1：把“能用”变成“稳定可用”

4. **模型网关补 Key 与容灾**：至少让 Qwen/Kimi/GLM 中一个 chat 预设真实可用；增加超时/失败后的受控 fallback，并给 Qwen/Kimi/GLM 补能力/成本画像。
5. **降低 Harness 冷启动成本**：60 秒冷启动不适合日常；需要预热、常驻运行时或更轻的首轮上下文。
6. **补全应用数据边界**：明确二进制文件的工具化读取规范；给材质库造一条真实数据验证，而不是 0 行表结构。

### P2：把“可观测”变成“可运营”

7. 增加按模型/工具/租户聚合的成功率、P50/P95、错误码、Token 成本看板。
8. 建立一组固定评测任务：问答、单应用读取、SQLite 查询、图像生成、权限拒绝、定时任务，作为每次发版的门禁。

## 七、最终判断

**平台 AI 能力已经跨过“完全没有”阶段，进入“真实底座可用、产品化不完整”阶段。**

它现在最值得肯定的不是预设数量，而是三条真实链路已经闭合：

1. 模型能真实回答；
